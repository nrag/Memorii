# SQLite Memory Payload Storage

Status: feasibility draft. The live partition continues to use the approved storage contracts in [storage details](memorii_storage_details.md) and [durable execution and solver runtime](durable_execution_and_solver_runtime.md).

The v7 partition repeats each newly admitted record in the immutable memory batch, the record version catalog, and the current record catalog. In the installed 128-source diagnostic those three catalogs accounted for 97.7% of the file. Acquisition spent 226 of 273 ms rebuilding the catalog manifest. On the 512-source diagnostic the physical file was 1.85 GiB for 128 MiB of source bodies. [Capacity evidence](../work/durable-delivery-implementation/validation.md)

## Proposed Physical Boundary

Store a canonical record's exact UTF-8 JSON bytes once per physical partition. Derive its payload coordinate with a domain-separated SHA-256 over the bytes, independent of the existing semantic record digest and batch checksum. Release continues to resolve a typed current or historical record identity before looking up its payload. Preserve scope, source kind, status, domain, logical forget behavior and provenance.

Keep the memory batch revision, data revision, original checksum, and creation metadata. Store the ordered batch member coordinates. Keep the existing version identities and current first-insertion order in signed catalogs. A current row refers to its latest authenticated version or the exact payload coordinate verified against that version. Compare every reconstructed batch, version and current row against the signed source during upgrade. Require complete ordinals and reject missing, substituted, duplicate, or unreferenced payloads. Preserve raw stored bytes where they differ from the serialization emitted by the current model. A converter must either preserve exact historical framing or reject the staged upgrade before cutover while leaving the original generation operable.

Evaluate raw storage first. An optional per-payload lossless codec needs a closed version, an authenticated raw byte length, a configured upper bound, and complete stream exhaustion. Reject truncation, trailing bytes, or decoded bytes that differ from the authenticated digest. Retain a raw codec for historical payloads beyond the compression limit. Authenticate decoded content before release. Record separate timings for decoding, content verification and SQL copy so a smaller archive cannot mask more expensive acquisition.

## Publication, Replay And Restore

The publication owner appends a payload when absent and updates batch membership, version refs, current refs, and the signed manifest in the same SQLite transaction. Exact retries reuse a payload only after checking its complete hash and byte length. The previous catalog root remains the precondition for incremental publication. Tier B scans each unique payload once and verifies the signed graph and runtime history. Logical first use and staged upgrade verify ordered semantic batch checksums. Earlier signed manifest algorithms remain readable for existing generations.

All storage reads that use the old JSON columns need an explicit binding before implementation. The memory-plane store owns decoding and still verifies logical batch checksums, revision order, and context increments. Runtime source authority must still prove that the current source and admission records equal their exact first versions and were written at the same revision. Checkpoint archive validation needs an authenticated task selector for the existing evidence query. Forensic export must still enumerate ordered versions and verify their content. Exact-current restore preserves its original data format. A format upgrade verifies source bytes under their original signed root, constructs a separate staging generation, and uses the existing owner-reviewed cutover and current suppression policy. The existing generation remains available for rollback as allowed by storage administration.

Current and historical references stay within a partition and its selected data generation. Logical forget continues to suppress identities and derivatives even when signed history retains their bytes. Selective payload deletion would change historical replay. Physical erasure continues through the approved whole-partition owner.

## Feasibility And Acceptance

Use the same verified 128- and 512-source fixtures for the v7 baseline and both experimental encodings. The experiment starts from a read-only source, writes an isolated scratch database, and compares all three reconstructed v7 catalog commitments against the original. The production service does not select the scratch database. Retain exact fixture and candidate identity and raw measurement boundaries.

A production implementation requires verified new-format acquisition, read and write parity, legacy upgrade and backup/restore fault tests, and the complete installed Linux and macOS reference workload. Three-catalog size and copy diagnostics identify likely savings. They do not certify a full backup pause or production acquisition.

The [Linux feasibility experiment](../work/sqlite-memory-payload-design/design.plan.md) reproduced all three signed v7 catalog commitments for both encodings. Raw deduplication cut catalog bytes by 66% on the 512-source fixture. Compression cut them by 81%, while hashing and decompressing each unique payload took substantially longer than reading and hashing the v7 catalogs. The probe checks only its experimental format, with 16 MiB per record and 64 MiB per batch. Those caps are not proposed constraints on the existing persisted format.

Carry forward raw storage as the first candidate. Benchmark a production-shaped acquisition path that reads the raw payload table sequentially, verifies each payload once, and authenticates the complete typed reference and selector catalogs separately. Keep logical batch validation and replay on their normal entry points and time the first memory-plane read so acquisition savings cannot come from moving the work. Use compressed storage as a separate experiment if the raw path meets the acquisition budget and backup still requires it. The existing v7 baseline remains an alternative until a replacement passes both budgets.

## Candidate Layout And Verification

Use an ordinary SQLite rowid table for raw payloads. The rowid determines scan order and has no application identity or reference meaning. Lookups target the unique 32-byte content digest. The authoritative payload commitment binds digest, exact byte length and codec. The body is bound transitively by recalculating the digest over the actual BLOB during Tier B. Compute signed metadata from the base table in digest order, compare the complete base-table `(digest, rowid)` mapping with the lookup index, then hash bodies in rowid order from the same snapshot. A covering index cannot supply the authoritative metadata. Validate or rebuild any other derived index that influences an authorized lookup. Use bounded reads without relying on mmap. Verify SQL types, the closed schema, payload lengths, reference closure, orphan absence and each header's exact nonnegative member count and contiguous positions. Empty batches retain their checksums and advance write revision without advancing data revision. Fail before releasing any acquired tuple on mismatch.

The batch header catalog binds `(revision, data_revision, checksum, created_utc, member_count)`. The ordered membership catalog binds `(revision, ordinal, memory_id, payload_digest)`. The version catalog binds `(memory_id, batch_revision, payload_digest)`. Tier B verifies that members and versions form a bijection on identity, revision and digest and that identities in a batch are distinct. The current catalog binds `(memory_id, batch_revision, payload_digest, status, domain, source_kind, insertion_order, task_id)`, with a nullable `task_id` and the existing BINARY memory ID order. Tier B checks that the current reference resolves to the latest retained version for its identity. Before signing either a write or conversion, validate that each bound identity and selector matches the typed payload. The signed write path adds unchanged content by reference, commits the graph and root atomically, and anchors the old root using the existing partition protocol. Verification still checks the closed schema and all other catalog and runtime history commitments and quarantines mismatches through the existing installation integrity path.

Retain the original logical validation of every batch prior to its first use. The memory plane validates checksums and revision transitions against the ordered typed members and releases the requested record only after the chain closes at the signed revision state. Stream the batch history within the same transaction. Treat acquisition and first read as separate measurements and report their sum as user-visible cold cost. Never trust a recorded checksum alone as proof that the original checks ran.

### Production Read And Migration Bindings

| Existing owner | Required binding for the candidate |
| --- | --- |
| `PartitionDataRepository` and materialization SQL | Select the exact format at reopen. Publish payload, header, member, version and current catalogs in one transaction. Enroll all changed keys in the appropriate signed accumulator and bind the payload identity and size to the signed root. |
| `SqliteMemoryPlaneStore` | Resolve current and historical candidates using the existing selectors and order, then decode authenticated bytes. Reuse the existing batch checksum and visibility rules for replay. |
| Runtime source authority | Resolve the initial and current source and admission versions by exact `memory_id` and revision. Require matching byte digests and the same originating revision. Preserve provenance and suppression checks. |
| Runtime checkpoint archive guard | Select typed, authenticated `task_id` evidence from the current-record projection without a JSON table scan. Preserve exact task scoping and existing refusal behavior. |
| Administration, forensic export and migration | Export historical rows in original order. For pending init and empty-partition checks preserve the distinction between missing and existing batches. Apply forget and suppression through the existing logical authorities. Verify and prepare the new generation under the owner publication lock before routing any live requests. |

The converter verifies the legacy owner and sealed tuple first. Establish exact parity of the original three catalog roots by reconstructing the legacy rows in staging, including original batch framing and serialized record bytes. The initial converter accepts an exact match to the deployed v7 writer's `PersistedBatch.model_dump_json()` byte framing only. A valid legacy batch outside that form leaves the source generation selected and returns an operator diagnostic identifying its revision and unsupported framing, without exposing payload contents. Earlier readable generations use the existing staged legacy upgrade before this conversion. Only finalize the new generation after the full candidate manifest, logical batch chain and runtime replay verify. A failed, interrupted or space-exhausted staging operation must leave verified v7 serving available under the existing rollback and suppression rules. Backup verification and exact-current restore must dispatch the verified archive's original manifest and storage format. Restore must still satisfy current authority before cutover.

Reuse backup `restore-preview-stage` and owner-authorized `upgrade-runtime`. Select the existing v4–v6 to v7 validation and conversion explicitly for that route. The current recovery upgrader keys off the latest format and refuses v1–v3, so merely increasing the highest schema version would change the route. Preserve existing v1–v3 handling. Preview identifies the source tuple and intended format and reports staging-space needs and framing incompatibilities before activation. Activation requires the reviewed preview digest and unchanged source authority. A source change requires a new preview. Record the new selected generation and prior recovery generation in the existing administrative result. After new writes to the selected generation, switching to the old generation follows the reviewed older-data restore path, including loss acknowledgement and delivery holds. Report resource and integrity failures without returning record bodies or silently falling back to unverified data. Keep fresh installations on v7 until the raw format has completed staged and platform qualification.
