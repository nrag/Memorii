# Production Custody For Sealed Startup

**Proposed design for an opt-in, owner-enrolled service installation.** Ordinary verified startup remains the default. Only named v8 generations in `read_only` can use a seal. Ordinary writable starts, explicit full verification and installations outside service custody keep the existing acquisition path. This proposal extends [Verified Startup](verified_startup.md). The [macOS prototype](../work/verified-startup/implementation.plan.md) proved acquisition on private copies through one SQLite read and closed its handles before declaring success.

## Owners And Enforcement

| Owner | Responsibilities |
| --- | --- |
| Trusted host supervisor | Enrolls one installation under a dedicated OS service identity, retains the enrollment and a content-free custody ledger outside the data and key trees, and enforces one running storage process. Owns the local endpoint identity and restart/drain boundary. |
| Managed storage process | Owns the registered installation root, control/key owner, all SQLite connections, existing `StorageAdministrationService` and operator entry points, prepared requests, and the sealed reader. Both the ordinary and sealed paths run here. |
| Clients | Use existing authorized runtime operations through the managed endpoint. An authenticated owner peer may invoke operator actions with an existing `OwnerCapability` minted inside the process for that installation. A harness receives its existing scoped authorization. Neither receives SQLite handles, data FDs, or direct access to the enrolled tree. |

Enrollment uses an administrator-provisioned dedicated service account and a local filesystem. Support fresh private roots created by that account. To move existing data, use the verified owner restore path into a new private tree with newly created data inodes. Track the previous root and any archives as independent copies for erasure. Disable in-place enrollment, including ownership changes or directory moves. Those actions cannot revoke a descriptor or mapping already held by a previous writer.

Protect the root and its ancestors, lockfiles, configuration and supervisor state from client UIDs and path substitution. The supervisor authenticates local peer OS identity and binds it to the selected installation and role. The principal running an old binary or a harness cannot write to the new root. Enrollment refuses shared UIDs, unsupported filesystems, untracked aliases, and deployments that still require external direct storage access. Initially expose only broker-composed operations with an existing authorized caller. No pathname or SQLite URI supplied by a client selects storage. The host administrator, supervisor, service process and current control/key owner are trusted. This raises the deployment requirement for the optional feature and leaves the existing control-authority compromise/rollback limitation in place.

The descriptor-owning worker holds an exclusive installation ownership lock on an inode anchored outside the replaceable partition. The supervisor starts a successor only after confirming predecessor process exit and obtaining ownership lock handoff. If either fact is uncertain, startup stays closed. On orderly close, release the ownership lock only after native views, data descriptors, response buffers and backup jobs have retired. The service uses close-on-exec descriptors and forbids fork, FD export and subprocess inheritance for data handles. After supervisor loss the worker stops request admission and exits. A successor reconciles the durable ledger before listening. A PID, timeout, or heartbeat alone cannot revoke a retained SQLite view.

### Current Code Boundaries

- `open_managed_partition` creates a mutable repository after normal acquisition. Add a separate, explicit composition in the managed service for a sealed read-only repository. Keep the shared row decoders and repository read methods. The normal SQLite repository configures WAL and owns write transactions. A sealed repository must reject write transaction, publication, raw write, writable fallback, and connection replacement before opening anything writable. A sealed verification result cannot populate the mutable forest or verification cookie. - Keep signed generation selection, current control, operation authorization, epoch, grants, forget watermarks, and release checks in `StorageAdministrationService` and the existing owners. The managed sidecar captures a concrete repository at construction; close and rebuild that composition at mode/handle change. It cannot retain a repository from an older owner. Route it through custody before constructing any writable handle or calling the existing transition. Backup, restore, format upgrade, retention, repair, trust changes, and erasure enter the same dispatcher. The broker cannot call a direct convenience method that bypasses that dispatcher. ## Retained SQLite View

**Choose a descriptor-bound, read-only SQLite VFS with block authentication.** Confirm the original `partition.sqlite3` is the selected inode, WAL is completely checkpointed and all writers are closed. Exclude SQLite side files and attached participants, symbolic/hard aliases, and detached replicas. Compute the candidate root and block table from that held descriptor, stay unavailable, then run every existing logical check through that candidate view: raw SHA-256 and reference/index parity, full catalog manifest, current publication, signed checkpoint and replay closure. Only then recheck control and custody, sign the candidate root and publish it durably. An unapproved candidate can never serve a runtime read. Normal operator backup may use registered copies, but the seal provider creates no copy, snapshot, mount, writable overlay or plaintext spill.

At startup the service authenticates a current control snapshot using the existing authority and reads the whole signed image through an owner-opened `O_RDONLY` descriptor. Use one full sequential pass to build a block digest table and validate its root before ready. The VFS opens the verified descriptor by a private process-local reference without resolving another path. Register it against the exact packaged SQLite build. Arbitrary opens, shared cache, attachment, raw mmap/`xFetch`, journaling, `xWrite`, truncation and extension loading after bootstrap are disabled. Permit internal volatile temporary work within a budget. All SQLite reads, including read-ahead, cross-block reads and BLOB access, go through `xRead`. [SQLite VFS](https://www.sqlite.org/vfs.html) · [SQLite file-open and immutable flags](https://www.sqlite.org/uri.html)

The implementation candidate is one bundled native extension built against the enrolled service's SQLite headers and loaded into a private bootstrap CPython `sqlite3.Connection` by absolute package-owned path. Pin and verify the extension and runtime build before loading. Use SQLite's extension API dispatch table, with no second linked SQLite library. Register under a private nondefault VFS name, disable loading before accepting work, and permit only a single-use private reference to the lease's pinned descriptor for a main read-only open. Reject nested, foreign and temp-file opens and never delegate data to the default VFS. Use memory temp storage with a fixed resource budget and return an unavailable result if a query exceeds it. The macOS ABI smoke test used the current CPython/SQLite pair to register a custom `xOpen` in the same runtime, verified that a named open reached it and verified that the default open still worked. It did not bind a descriptor or read a real retained SQLite view. [ABI smoke test](../work/sealed-custody/sqlite-abi-macos.json)

The checksum format for production is version 2 of the proposed `verified_image.json` seal, using a separate purpose `memorii.verified-image.v2`. Use the identity, publication, control tip, trust, signer, schema, and verifier profile fields from the [startup design](verified_startup.md#seal-authority-and-failures). In that closed format replace the flat image SHA-256 field with `image_root`, a lowercase 64-digit hex digest, and retain the signed positive byte length. The explicit format version selects the fixed block profile and signing purpose. Reject duplicate fields, unsupported versions and noncanonical types. Sign the canonical JSON digest of all fields except the signature. Authenticate before stale classification.

- Block size is 65,536 bytes. For block index `i`, hash `b"memorii.sealed-image-block.v2\0" || u64be(i) || block_bytes` with SHA-256. There is exactly one final short block if needed. The signed positive image size fixes every block length and the block count.
- The image root is SHA-256 of `b"memorii.sealed-image-root.v2\0" || u64be(image_size) || block_digest[0] || ...`. Check offsets and count before allocation, read exactly the declared bytes from one descriptor, confirm EOF and custody, and compare the authenticated root before publishing readiness. The initial deployment image size cap is 8 GiB. The 4 MiB ceiling for its digest table is checked before reading. A larger image uses ordinary exact acquisition. Prototype v1 seals are ineligible for this production certificate.
- Retain the table only in the storage process, bound to that descriptor, current authenticated authority and issued lease. `xFileSize` reports the signed size. Validate nonnegative, nonoverflowing ranges before `pread`. On each physical block read, hash the actual buffer before copying any bytes to SQLite. A verified immutable in-memory buffer may be reused in a bounded 16 MiB block cache. SQLite's own page cache can contain only data supplied by this VFS and observes its separately configured limit. No cache survives file or handle change. Zero-fill the part beyond signed EOF and return `SQLITE_IOERR_SHORT_READ`. A short read within the signed size, mismatch, or custody failure latches an integrity denial for the entire lease. A cross-block read commits no protected output until all required blocks pass. [SQLite I/O contract](https://www.sqlite.org/c3ref/io_methods.html)

Startup still hashes every byte. Logical checks at issuance apply at startup because the returned SQLite view is derived from the identical authenticated bytes. The per-block check also covers corruption encountered after readiness. Seal issuance binds all pre-existing exact integrity checks. It cannot assert a seal for an unverified copy. A second exact check through existing `doctor`, backup verification, restore, and migration still uses the full logical verifier. No weaker source of freshness such as inode metadata or a persisted digest table replaces either proof.

Keep the descriptor, the single native read-only connection, all derived cursors, and any pending response in one lease. Start every protected operation by checking current Tier A, current authorization/suppression and lease identity. Check the latch and current authority again under the release fence before handing off a response or page cursor. No protected output is authorized after the drain or a latched failure. Already released bytes are outside process custody. A cursor or failed query cannot publish its partial output. Query results, cached pages and buffers are disposed with the lease. Losing trust, eligibility, selected generation, suppression watermark, or control custody closes admissions and retires it. A fresh sealed acquisition is possible only for an eligible current seal. Unavailable backing authority is a denial. A missing or authenticated stale seal on a clean, known state can go through ordinary full acquisition after safe handoff. A same-coordinate corrupt seal, image mismatch or lost custody denies without fallback.

The existing sidecar socket write occurs after the verified response is constructed. For sealed serving, serialize into a bounded owner-held buffer. Take the publication fence and then the lease release mutex to recheck the active lease, request authorization and current authority before each bounded nonblocking socket write. The native integrity latch uses that same mutex and never acquires the publication fence. The kernel accepting bytes is the release point. If the socket would block, release both guards and retry only after rechecking all conditions. Drain or revocation cancels unsent buffers and closes an incomplete response. Clients must treat an incomplete framed response as failed. A slow peer never holds the publication fence while waiting. Data accepted by the kernel before revocation or drain is already released. [Current socket handoff](../../memorii/memorii/core/harness_state/sidecar.py#L603)

Grant creation and epoch changes, grant revocation, and credential issuance, retirement and rotation all enter the managed dispatcher and take the publication fence before their existing registry locks. Direct registry writers must be unavailable in an enrolled deployment. The existing read-grant mutation takes its own registry lock and thus needs this additional composition. Any alternate grant resolver must be ordered by the same fence, or its routes are ineligible for sealed serving. This makes grant and credential changes mutually exclusive with the final authorization check and nonblocking write. [Read-grant registry](../../memorii/memorii/core/harness_state/grant_registry.py#L55)

## Durable Transitions And Lock Order

The protected supervisor ledger records one installation, enrollment, and at most one pending operation. A closed versioned record binds the operation, source mode and signed tuple, expected control revision, target action and its exact request digest, operation idempotency key, and any owner-confirmed erasure plan and inventory. The ledger uses a supervisor-owned SQLite database outside the managed data and installation-key trees. Use full sync, atomic compare-and-swap and a monotonic revision; sync the parent when creating the ledger. Sign records with an independent supervisor key whose public identity is pinned by host enrollment. This key cannot decrypt data or sign a runtime/control publication. The ledger holds no source text or database pages. An unresolved, unverifiable or unreadable ledger closes admissions on every supported entry point.

| State | Admission and recovery |
| --- | --- |
| Ordinary | Use existing storage, recovery, and logical acquisition. Owner sealing first enters the existing `read_only` barrier. |
| Sealing | Close all write/open paths, drain cursors and writers, checkpoint and close WAL, and run exact verification on the pinned image. Durably install the signed seal before changing the ledger to sealed. A seal found while the ledger is still sealing cannot admit reads. Recovery rechecks authority and restarts sealing or owner-aborts back to ordinary read-only verification. |
| Sealed | The matching issued seal is current and admits a closed read view only. A process restart fully revalidates it, including a new byte scan. |
| Draining | Under the publication fence persist closed admissions and deny new work. Release the fence while waiting for every in-flight response, read transaction, cursor and retained connection to finish or be cancelled. Close SQLite and the descriptor, dispose volatile caches, then release the shared lifetime guard. Timeout returns busy with admissions closed until a recorded owner retry/cancel or proven supervisor teardown. |
| Writable transition | With no sealed holder, reacquire existing lifetime/publication custody, authenticate current authority and original transition, durably retire the seal, and recreate the ordinary SQLite owner with a fresh verified manifest. Perform the existing mode change or generation publication and recover its ordinary intents. Admit requests only after exact verification and successful authority handoff. |
| Erasing / erased | Erasing admits no client read, sign, restore, init or activation routes for the installation. Finish only according to the independent deletion ledger and receipt rules below. Both terminal outcomes keep this installation identity unavailable. |

The ownership lock is outermost. A live seal holds the **existing shared backup lifetime guard** from pin through closure. For request/release and physical operations the existing order remains lifetime guard, publication fence, partition lock, then control transaction. Draining may briefly take the publication fence while the live shared lifetime is held. It must release the fence before waiting for reader teardown. Acquire exclusive lifetime only after all shared owners retire, then take the publication fence and revalidate the pending operation, mode, generation, epoch, key/trust and current control tip. Reuse those existing operator lock scopes or factor their already-fenced core operations. Recursive lifetime or publication locking is prohibited. A phase restart reconstructs state from the supervisor ledger and signed control/generation intent. It never chooses a detached or expired seal by path discovery.

Activation uses the same selected inode after every sealed holder and copied handle is gone. Reopen in ordinary WAL mode, resolve or deny pending work, acquire the exact logical state, and let the existing owner mode change and forget-enforcement drain run. The first writer uses `_require_materialization_base` on its current writable connection. Restore or upgrade use their existing staging generation and signed pointer finalization after drain. Seal retirement before activation cannot be undone by restarting, rolling back package code, or copying an old seal. To seal again, explicitly enter `read_only`, re-verify, and issue a new seal. Rolling back to a binary without custody support requires an explicit owner unenrollment while drained, full verification through the ordinary path, and the existing compatibility/rollback checks. Package downgrade cannot directly regain filesystem access.

Read-only status and authorized state reads may use the sealed path. Commands requiring data mutation are denied while sealed. Forget, grant or trust revocation makes affected releases ineligible immediately under ordinary controls. A control-only authority change retires the seal; any dependent data enforcement must go through the ordinary owner transition. For the first release, explicit doctor and backup take an owner-authorized drain into ordinary read-only maintenance, run their existing full verification using their existing lifetime and publication scopes, and leave the installation ordinary until the owner explicitly reseals. This avoids a second path-based SQLite connection while the sealed lease is held. The archive and restore formats retain their existing authority. The seal and supervisor ledger are excluded from backed-up or restored data authority. [Current backup source and locking](../../memorii/memorii/core/storage_administration/operator_backup.py#L368)

## Erasure

Today `apply_erasure` takes the exclusive backup lifetime followed by publication, removes the partition and installation keys, then writes control and a receipt. In the enrolled configuration that sequence needs a restartable handoff because the provider introduces live references and control signing can be unavailable after key removal. [Current erasure](../../memorii/memorii/core/storage_administration/operator_governance.py#L878)

1. Resolve a current owner-authorized plan and a separate explicit destructive confirmation. Bind them to the enrolled owner peer, installation, operation identity, exact inventory version, acknowledged manifest and current authority. The inventory includes the sealed file, seal, live leases and caches, every generation and stage, SQLite side files, spool and derived storage if present, registered backups/copies and keys. Include any registered backup staging artifacts governed by the existing lifetime lock. Abort on shared or unknown managed storage. Independently held copies may leave the result `erasure_incomplete`. A dry-run creates no terminal receipt.
2. Before deletion, durably write the authenticated erasure intent in the supervisor's independent ledger and close admissions. Drain readers, writer jobs, backup holders and unpublished response buffers outside the publication fence. Revalidate plan and inventory under exclusive lifetime and publication before starting deletion. Crashes or cancellation after the destructive phase leave erasure pending with admission closed. A stuck owner or missing inventory cannot produce an erased receipt.
3. Remove tracked data/copies and their keys using the existing owner deletion semantics with no-follow participant inventory. Sync containing directories and record durable progress for each verified deletion. Verify there are no open managed data views, no stage or provider artifact, no selected generation path or accessible alias, and no surviving wrapped data key. The erasing worker may perform one allowlisted internal signing action for the final control journal entry while the installation signer is live. Store that signed entry's digest, verified managed-inventory outcome and the expected installation key coordinate in the independent ledger before granting permission to remove the signing key. This intermediate control entry is never a public completion receipt. Close the installation owner and prove process exit so even cached private keys and native handles are gone.
4. The supervisor removes the confirmed signing key last, syncs its containing directories, checks absence, and commits the terminal ledger record. With the authenticated pre-unlink record and worker teardown proof, a restart may repeat the exact unlink or confirm it already occurred. Unexpected key absence before that record, or key identity substitution, leaves erasure pending. Boot erasure recovery from the independent ledger before creating `StorageAdministrationService`. The terminal receipt is content-free and signed by the supervisor. It binds installation, original operation identity, closed outcome `erased | erasure_incomplete`, and completion time. Store it once before acknowledging. After signer loss a peer matching the original durable owner authorization may query or resume that exact confirmed operation only. The operation ID alone supplies no authorization and cannot authorize another deletion.
5. External copy uncertainty leaves the result explicitly `erasure_incomplete` after all managed deletion is proved. Unknown or inaccessible managed state, failed fsync or incomplete key deletion keeps erasure pending. Suppression, retirement and a stale seal are insufficient evidence for deletion. This protocol tracks custody and deletion of managed bytes. It provides the existing scope of erasure, with no media overwrite guarantee or retraction of responses already delivered. [Erasure requirements](durable_execution_and_solver_runtime.md#forgetting-erasure-and-retention)

## Evidence And Release Gates

| ID | Requirement and evidence required |
| --- | --- |
| VC-01 | An enrolled service is the sole native owner. Test ordinary clients, old binaries, wrong local peers, symlink/hard-link paths, orphaned worker and restart. Keep a writable descriptor or map on the previous root during verified import and show that it cannot touch newly enrolled inodes. |
| VC-02 | Seal proves exact same bytes through retained native SQLite operations. Test old/new profile byte vectors, arbitrary equal-length corruption before issuance and after seal, swapped descriptor/path, WAL/SHM/journal and attach, cross-block/short-read/mmap cases, and retained view through multiple authorized requests. Pause between authorization recheck and send, and exercise both lock orders for grant revocation and credential rotation. Latch corruption while a response is buffered. No response bytes may be authorized after the competing mutation or latch. |
| VC-03 | No overlap of sealed custody with active or replacement writers. Pause an existing reader or backup while closing admissions, then test both drain orders, timeout, process death, restore, upgrade, mode/forget transitions, stale request and same-key retry. Only the original signed publication protocol may finalize a generation. Confirm fresh writable manifest and full audits. |
| VC-04 | Erasure closes all managed copies before acknowledging. Test skipped confirmation and foreign plans, surviving lease/backup/stage, unknown external inventory, failures before or after every durable deletion and signer-loss boundary, crash-retry and lost acknowledgment. Verify restart denies access and completion survives destruction of installation keys. |
| VC-05 | Preserve ordinary startup and release boundaries. Fresh v8 uses ordinary verification. Run exact balanced/concentrated startup on supported native macOS/Linux, with ready-through-service and acquisition reported separately, and measure retained read overhead and read-only-to-active/erase pause. Preserve the governing sample sizes and apply the 11 s acquisition gate. |

The native macOS [block-table spike](../work/sealed-custody/block-hash-macos.jsonl) computed the proposed root on the two exact retained main-image byte streams from zero-residency copies. It took **2.90 s balanced** and **2.48 s concentrated** with about **2.76 MB** of digests per image. This times hash and table creation only. It adds no execution proof of SQLite VFS binding, native service isolation, or the full startup acquisition gate. The existing private prototype remains separate. [Private prototype results](../work/verified-startup/implementation.plan.md#native-results)

Alternatives considered: owner-settable macOS flags aid the private experiment but leave production authority with the same UID. Linux fs-verity can verify individual reads successfully, while measuring its root alone leaves unread corruption undiscovered at readiness and needs a filesystem-specific deployment. A database dump or snapshot copy incurs storage and erasure obligations and can mismatch the selected authority. The descriptor VFS and sole managed owner avoid a second persistent image and keep the same startup detection boundary. [macOS file flags](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/chflags.2.html) · [Linux fs-verity](https://docs.kernel.org/filesystems/fsverity.html)

**Approval boundary.** This document proposes a production architecture. Before fast startup can ship, the governing Tier B definition must explicitly allow the authenticated byte-equivalence path for this enrolled immutable read case. Keep its current exact recomputation requirement for other opens and explicit audits. Also qualify the native VFS, broker isolation, and restartable erasure on the actual supported artifacts.

Proposed Tier B amendment for that review: an enrolled read-only acquisition may establish the exact logical Tier B result by matching a complete authenticated byte image to an owner-issued descriptor-bound seal created by the full current verifier. This requires current Tier A and signer/profile checks, successful whole-image authentication before readiness, and authenticated reads through the retained view until retirement. Ordinary writable acquisition, recovery, explicit full verification, and paths without proven custody continue to run Tier B as currently specified.
