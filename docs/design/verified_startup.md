# Verified Startup For Managed Storage

**Proposed design.** The installed default remains v7. The first cold-start experiment covers owner-staged v8 named generations in read-only mode. The current acquisition remains the default path for a new process serving a writable generation.

The [production custody proposal](sealed_startup_custody.md) specifies the enrolled storage owner, retained SQLite view, writer handoff and erasure protocol.

## Why Startup Scans

`open_managed_partition` creates a fresh `StorageAdministrationService` and calls `acquire_verified_snapshot` before returning the memory plane. The constructor verifies the independent control journal. Acquisition holds the publication fence, resolves pending publication, loads the signed finalized tuple and checks the selected SQLite generation. On a cache miss, `_matches_materialization` verifies raw bodies, schema, references and index parity, rebuilds the catalog forest, compares its digest, and verifies checkpoint plus tail against the signed head and live rows. A valid checkpoint skips journal prefix replay. It supplies no current evidence for raw bodies or materialized SQLite tables. [Factory](../../memorii/memorii/core/persistence/factory.py#L283) · [Acquisition](../../memorii/memorii/core/storage_administration/service.py#L988) · [Exact verifier](../../memorii/memorii/core/storage_administration/service.py#L1095)

`_verified_tuples` and the manifest accumulator live in the service and its SQLite handle. The guard checks generation, signed tuple and the connection's SQLite verification cookie. A restarted process has neither cache nor a connection-local witness of intervening writes. A signed old digest, inode, file timestamp, SQLite counter, cached forest, or sampled checksum cannot establish what bytes a new process has opened. The release contract requires detecting an arbitrary preserved-head row mutation at verification acquisition. A portable cold path must inspect the bytes or obtain an equivalent whole-image guarantee from an independent trusted authority. [Existing integrity contract](durable_execution_and_solver_runtime.md#closed-publication-and-control-authority)

## Two Startup Paths

| Path | Eligibility | Work before protected data release |
| --- | --- | --- |
| Harness reconnect | Harness uses an already running, acquired managed runtime sidecar | Existing credential and grant checks, current Tier A checks, and full verification on existing cache invalidation. |
| Cold open of a sealed read-only image | Explicit owner staging, current named v8 generation, clean control state, approved verifier profile, immutable view with exact byte proof | Validate the control journal and current publication, stream and hash the complete selected image, authenticate and compare its seal, and check live SQLite publication coordinates. |
| Other cold open | Active or v7 generation, absent or stale seal, unsupported view, or explicit full verification | Existing exact logical verification and recovery path. |

### Keep Runtime Ownership Across Harness Restarts

Run the installed runtime sidecar under an independent lifecycle and acquire once in that process before opening its listener. Keep one administration service and the SQLite partition owner it verified. A restarting harness connects to the existing loopback API and obtains an authorized current state response. Use `RuntimeSidecar.for_managed_installation` with the existing credential store, grant resolver and spool. Every request still passes the existing handler and `verified_operation_context` where required. This first scope covers only the sidecar's existing runtime endpoints. For example, Hermes local memory ingress currently opens its own managed partition. It gains no shortcut until it has an explicit, separately designed hosted memory API. [Sidecar composition](../../memorii/memorii/core/harness_state/sidecar.py#L210) · [Hermes local authority](../../memorii/memorii/integrations/hermes_local_authority.py#L246)

The sidecar process remains responsible for verification after its own restart, handle loss, generation change or externally published tuple. Client restart neither creates a new storage acquisition nor grants access. A listener that has not acquired the current head cannot serve task content. Existing revocations, grants, paging, publication, and recovery checks remain authoritative. Lost responses use existing idempotency and origin-proof behavior. No detached cache, reusable readiness token, or state transfer between SQLite connections is introduced.

The existing loopback server is threaded inside its caller and has no packaged launcher. The experiment must start it from a separate owner-provisioned process and connect two successive installed clients. The owner supplies the exact installation root, the existing owner-protected credential directory and spool for that root, and the trusted runtime grant resolver. This process opens through `open_managed_partition`, constructs the managed sidecar with that returned owner, and starts its listener after acquisition. On a stale-generation or closed-handle result it stops protected responses, closes the old sidecar and repository, and rebuilds the composition through the same factory before release. An integrity or recovery denial stays unavailable. Pass endpoint identity through the operator-controlled bootstrap. Production packaging and discovery must authenticate the intended local peer before sending credentials. Loopback addressing alone provides no peer authentication. An unavailable or unauthenticated endpoint denies the reconnect.

### Seal The Exact Read-Only Image

The seal is an optional signed proof produced by the owner. Its meaning is limited to one byte-exact SQLite image and one current finalized publication. At seal time, the whole logical verification runs. At cold open, authenticating every image byte proves that the already verified logical checks apply to the current immutable view. Hashing a detached good copy while serving a different database would break this implication.

1. An owner capability invokes sealing after the existing `read_only` barrier. Require a named v8 generation, a clean signer and control journal, no pending publication or prepared generation change, and the current operational control state. Under existing publication-then-partition lock order and storage custody, make the **selected** data participant a self-contained SQLite image. Complete WAL checkpointing and exclude live WAL, journal and attached participants. Establish the read-only view before verification. A provider must give SQLite and the hashing reader the same stable object for the lease lifetime. Failure to establish custody leaves sealing unavailable.
2. Run the existing exact Tier B verifier on that view with no cache shortcut. This includes raw SHA-256, catalog rows and index parity, replay checkpoint signature and membership, prefix and anchor, exact tail and live projection equality. Only after success hash the image and issue the seal using the current authorized local key. Recheck control and view authority under the fence before atomic publication of the seal. An interrupted issue leaves either no seal or the complete signed seal. It creates no new tuple or runtime event. The online backup path can supply a staging technique, but its verification of a detached copy cannot authorize opening the selected live participant. [Backup snapshot](../../memorii/memorii/core/storage_administration/operator_backup.py#L322) · [Staged verification](../../memorii/memorii/core/storage_administration/operator_backup.py#L1278)
3. At automatic cold acquisition, the factory asks storage administration for a verified read-only open before constructing the runtime store. Validate the control journal and resolve pending work on the ordinary path first. If recovery was required, use ordinary full verification for that open. Under the fence, match the current selector, mode, generation, publication digest, control tip, trust state, signer, and approved verifier profile to the seal. Pin a read-only lease for the selected image. Stream and hash **all** bytes of that immutable view outside the publication fence. Reacquire the fence, revalidate authority and lease identity, and check that the same lease supplies the SQLite read handle. Perform the existing publication, revision, and schema checks. A typed in-process result can satisfy acquisition for that handle only. It carries no writable materialization forest.
4. Keep that lease until the last derived handle closes. A new writable open uses ordinary verification and acquires its own exact accumulator. Any activation, restore, migration, repair, or file replacement must retire sealed readers before mutating or replacing their data. Under the publication fence, close admissions and mark the provider lease draining, then release the fence before waiting. Existing readers can need the fence to finish. Wait for a bounded drain or return busy without changing storage. Reacquire the fence and recheck current authority and exclusive custody before mutating. The provider must enforce this across processes, including aliased paths and binaries unaware of the seal. Then proceed through existing owner-controlled mode, publication, and generation protocols. A signed seal for an older tuple cannot follow a restore or waive current suppression, trust, or eligibility rules.

The implementation must provide a dedicated read-only repository open. The current `PartitionDataRepository` configures WAL and can open for write. Merely passing SQLite `immutable=1` asserts immutability and disables change detection. It creates no custody. The filesystem provider must enforce the stable readable view, bind both consumers to it, and exclude stale WAL and rollback-journal views. A private test fixture with no other writers is sufficient to test the proof, while release custody requires its own platform-specific implementation and tests. Opening a second descriptor inside the existing SQLite-owning process can interfere with native file locks. A separate hashing process or a proven SQLite integration owns any additional descriptor. [SQLite URI options](https://sqlite.org/uri.html) · [SQLite WAL and read-only databases](https://sqlite.org/wal.html)

Issuance and acquisition use a pinned, authenticated control snapshot under the publication fence. Validate the journal in the same control view that yields its exact tip, current operational mode, pending eligibility increments, suppression watermark, finalized tuple and applicable trust policy. Obtain current signer identity from its owner, including current authorization for this purpose. Constructor-time journal validation followed by reading a later tip is insufficient. On return from off-fence I/O, revalidate that authenticated coordinate and the image lease before publication or admission. On every protected operation, perform the ordinary Tier A and current grant, epoch and suppression checks and confirm that the admitted control coordinate and lease remain usable. A changed coordinate retires the lease and requires reacquisition. [Control journal validation](../../memorii/memorii/stores/sqlite/control.py#L231)

Enroll retained image leases and any physical provider artifacts in the installation's erasure lifetime. Keep the existing lifetime-before-publication ordering. The erase path already takes the exclusive backup lifetime guard. A sealed reader must share that lifetime guard for the entire view, or an equally enforced provider must block erase until the lease and all artifacts are gone. When an explicit drain is needed, request it under the fence, drop the fence, then wait for exclusivity. Forget or revocation follows the live control rules immediately and must retire any newly ineligible view. Physical erase can report completion only after retained sealed views, aliases or provider copies have been removed. An untracked native snapshot is ineligible. [Existing erasure path](../../memorii/memorii/core/storage_administration/operator_governance.py#L929)

### Seal Authority And Failures

- Proposed artifact `verified_image.json` resides in the control owner's storage. One active slot per installation, atomically replaced and directory-synced. Its closed record contains format version, installation and repository IDs, generation ID, exact publication digest, control-journal tip, eligibility epoch, trust-registry digest, partition schema, verifier-profile digest, image byte length, image SHA-256, signer key ID and fingerprint, and signature. Sign the existing canonical JSON digest of the unsigned fields with a new purpose `memorii.verified-image.v1`. The current configured control key owns signing. A caller supplies neither signer, alternate image path, nor verifier profile. Decode with strict types, a bounded size, and a closed version. Never load serialized trees or replay state from the artifact.
- The profile identifies the approved installed verification implementation, schema and SQLite compatibility envelope. The implementation plan must specify a build-owned profile identity and conformance tests for changes to validators, serialization dependencies, and SQLite behavior. A profile change forces full verification before a new seal can be issued. Hashes are SHA-256 with fixed encodings and integer bounds. The profile and control authority enter the signed comparison, so filesystem metadata is used only to reject races or unexpected objects.
- On the eligible path, authenticate the seal before classifying it as stale. Canonical field ordering is independent of on-disk JSON object order. Duplicate keys, unknown versions, extra or missing fields, invalid signatures, or untrusted signers are integrity failures. A missing seal, an authentic seal for another coordinate or verifier profile, or a clean unsupported view before pinning goes through exact logical acquisition. An eligible seal with a byte/length mismatch, unexpected participant, or custody loss after pinning produces the existing integrity denial with zero protected output. If authority changes during hashing, deny this acquisition and restart through current authority on a fresh attempt. Preserve diagnostics and let the owner run existing full verification/recovery explicitly. An expired, revoked, or replaced authority never advances through the sealed route. An OS view failing after ready denies further release and requires reacquisition.
- The seal is an accelerator. Deletion loses the accelerator and triggers full checks. Old binaries and restores may ignore it and use the existing storage format. Doctor, backup verification, restore, migration, and any explicit full audit always execute Tier B. No seal may be signed over an unverifiable participant or included as restored control authority.

## Alternatives And Evidence

| Alternative | Disposition |
| --- | --- |
| Process-local cache persisted on disk or signed again at shutdown | Reject. A new process still lacks proof about the current contents or missed writes. |
| APFS snapshot, file permissions, immutable bit, or SQLite cookie alone | These can help establish a stable read view. They provide no complete content attestation for the current image. |
| Merkle proofs or Linux fs-verity on read | Useful for integrity at access time. An unread corrupt page can remain undetected at ready, which changes today's detection boundary. Consider only with a separately approved contract or a trusted full scrub before release. [Linux fs-verity behavior](https://docs.kernel.org/filesystems/fsverity.html) |
| Full sequential byte authentication of an already verified image | Prototype. It preserves the before-ready detection boundary and shifts row, tree and replay work to sealing time. Runtime still reads the complete image. |
| Full logical verification of active writable storage | Retain. An exact writable cold fast path would need independently authenticated storage or versioned immutable participants plus authenticated changes. Neither is supplied by the current mutable SQLite/WAL architecture. |

The raw scan, non-raw manifest and replay together took approximately 9 seconds in the preceding exact-fixture experiment. A fresh-process feasibility spike hashed one zero-residency main-file copy per distribution on the native Mac. Balanced was 5,655,961,600 bytes in **2.41 s** and concentrated was 5,660,487,680 bytes in **2.19 s**. These numbers measure sequential SHA-256 only. The spike excluded control validation, establishing custody, SQLite startup and full seal issuance. It proves neither 5-second acquisition nor a safe native view provider. [Prior acquisition measurements](../work/reference-capacity-debugging/manifest-replay.plan.md) · [Byte-hash samples](../work/verified-startup/image-hash-macos.jsonl)

## Requirements And Acceptance

| ID | Requirement and source | Acceptance |
| --- | --- | --- |
| VS-01 | Preserve default and release authority. User request and current Tier A/B contract. | v7 initializes and opens through current paths. Exact authority/tuple checks remain before every release. Explicit audits execute the original logical verifier. |
| VS-02 | Keep one verification owner for live harness reconnect. Existing managed sidecar and factory boundaries. | Two installed harness client processes restart against one acquired sidecar. A normal reconnect runs zero full scans. Revoked credentials, grant expiry, external publication and daemon death exercise current deny or reacquire behavior. |
| VS-03 | Cold reuse proves the exact current image and profile. Current preserved-head detection boundary. | Both signed fixtures pass complete seal-time verification and reopen through byte authentication with zero raw, catalog rebuild, or replay calls during eligible startup. A single-byte mutation anywhere in a committed raw body, catalog/index, checkpoint, or event batch prevents ready. |
| VS-04 | Preserve custody and ordinary failure behavior. Control, restore and SQLite contracts. | Use barriers at journal validation, hash-to-open, ready-to-read and transition-to-drain. Substitute a detached copy or a new inode. Test hidden journals, valid stale and malformed seals, authority changes including forget and key rotation, and ordinary pending-intent resolution. Crash each issuance boundary. Prove no writable request can inherit the seal or its handle and no erasure completes with a surviving managed view. |
| VS-05 | Measure cost and lifecycle limits. Use the governing 10 s reference acquisition gate. | Report seal time, bytes and extra disk use, hash/lease/acquisition time, service-open time, owner outage and reconnect separately. Stage copies of the original fixtures and demonstrate that mode and image preparation preserve the logical manifest and replay position. Prototype on native macOS and Linux. A read-only pass is diagnostic. Release qualification still covers active cold startup, first service of externally published tuples and explicit verification with the governing acquisition paths and sample counts. |

For VS-03 and VS-04, use equal-length preserved-head mutations after sealing and corruption before issuance. Count logical verifier calls to distinguish normal fast release, exact fallback, and integrity denial. Check for zero protected results in every denial arm. For VS-02 record process identities and full acquisition counts separately for client and owner restarts.

No production behavior is approved by this draft. The current Tier B text specifies recomputation or an existing in-transaction equivalent. Adopting cold reuse requires an explicit governing design amendment authorizing the whole-image equivalence and a reviewed immutable-view provider for each enabled platform. Keep the cold path experimental until those gates pass. A long-lived runtime does not require that amendment because it stays attached to its existing verified owner.
