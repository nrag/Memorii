# Learned Ontology For Scoped Agent Memory

**Status:** Design approved on 2026-09-25 under `docs/work/learned-ontology/design.plan.md`. Not implemented.

**Product direction:** Memorii learns ontologies from scoped evidence supplied by agent integrations. The earlier Hermes trial recorded this direction; it does not own the ontology contract. Work and evidence: `docs/work/learned-ontology/design.plan.md`.

## 1. Problem and first useful journey

Memorii receives memory sources from different agents, harnesses, channels, and tools. The shipped base catalog must handle common organizational and at-home claims immediately. Those sources will also expose concepts and relations outside any fixed base. The ontology-learning journey for a genuine gap is:

1. An authenticated adapter submits a source with its principal, scope, and provenance. Core retains the original scoped evidence. If no ontology observer is available, the source receives a visible pending observation and no schema candidate or unsupported fact is invented.
2. A coverage observer verifies a missing relation or subtype, and core groups independent occurrences within the authorized catalog scope. On a recurrence trigger, an available model or authorized owner proposes one bounded additive edit, with source references and parent catalog identity.
3. Deterministic validation checks type, scope, domain routing, existing-name collisions, policy completeness, and compatibility. Evaluation compares the candidate with its parent on supported and withheld examples. The scope's authorized activation policy makes a recorded owner decision or an owner-enabled, calibrated automatic decision.
4. Acceptance publishes an immutable catalog version in the authorized scope and atomically selects it for future operations. A request already in flight keeps its previous version.
5. Eligible retained sources are reconsidered through ordinary source preparation, proposal, semantic validation, writer, and protected read. Catalog acceptance alone commits no fact.

The ontology learner is a core service. No adapter may select catalog meaning, validate its own proposal, or activate a version. A local CLI, a delegated agent, or a bot channel can supply evidence only through the same authenticated source contract and the scope grants available to that integration.

The source contract carries `source_id`, content digest and retained artifact reference, authenticated principal and agent identity, source and intended fact scopes, source classification, observation time, and the grants governing retention, discovery, and replay. An adapter may supply a claimed upstream origin, but core derives the authoritative lineage key only from authenticated delivery identity and a verified upstream origin receipt bound to immutable source bytes. If a common origin cannot be verified, core conservatively coalesces equal content digests within one catalog scope and does not count claimed distinct lineage IDs as independent evidence. Different verified upstream origins may count separately even when wording matches. A forwarded source with a changed digest but the same verified upstream origin remains one lineage. Missing or conflicting provenance is retained or rejected under source-admission policy but never counted as independent schema evidence. Equivalent authorized transcripts from different agents enter the same core path without giving either adapter catalog authority.

## 2. Baseline and governing boundaries

The current implemented example is the installed `memorii.project_assertions@1` profile. It binds packaged prompt, output schema, catalog, component fingerprints, and local authority digests. `ProjectAssertionProviderProposalAdapter` accepts only three predicate IDs and branches on their value type. `CurrentBootstrapV3RequestMaterializer` constructs a three-entry `PredicateProposalCatalog`; current trust, temporal, and state rules also enumerate those IDs. The generic `PredicateProposalCatalog` itself accepted a fourth entry in a 2026-09-25 in-memory feasibility check, and generic V3 terminal plumbing can handle a registered relation. A bounded read-only production-root probe found no path that can carry a fourth relation through the installed profile: package verifier, materializer, provider schema/adapter, and planning state rules all close over the same three IDs. The fourth relation cannot be tested end to end against the real installed root until those authorities change. The design therefore requires one generated catalog-owned binding across these owners; it does not claim ingestion, persistence, recall, or activation for a fourth relation today.

The Hermes Docker trial proved completed-turn admission, semantic commit, later-session recall, and restart for one registered relation. It is one integration baseline, not ontology-learning evidence or a prerequisite for another agent integration.

Gap discovery is separate from fact extraction. The current three-ID model output cannot report an unknown relation, so it must not be repurposed as a schema learner. A core-owned coverage monitor records deterministic ingestion, retrieval, and correction signals from authorized sources. When a compatible model capability is available, a semantic observer may classify retained source spans as `unsupported_relation` or `unsupported_entity_type`; without one, unexamined text remains queued and no gap is invented. A separate learner may propose a typed edit only from eligible observations. Neither observation nor proposal enters the fact writer. Discovery runs after source retention, so a model outage or invalid ontology proposal does not change source admission, existing-catalog retrieval, or already committed facts.

The semantic observer accepts source content only when its authenticated origin, grant, and domain policy permit ontology discovery. Its closed output is `no_gap`, `unsupported_relation`, `unsupported_entity_type`, or `uncertain`. A relation gap cites exact assertion, subject, relation phrase, and object spans; a type gap cites exact entity mention and context spans plus a proposed registered parent type. Both carry the core-verified source lineage. The observer checks whether an active catalog relation, type, or alias already covers the meaning before opening a gap. Missing or malformed spans, a question, command, quotation, report, unsupported speaker attribution, or an untrusted tool result become `uncertain` or `no_gap` without a catalog candidate. Its outcome is diagnostic metadata attached to retained evidence; it cannot mutate fact lifecycle.

The canonical source and memory-domain distinctions in `docs/design/memorii_spec.md`, `docs/design/memorii_storage_details.md`, `docs/design/event_model.md`, `docs/IMPLEMENTATION_RULES.md`, and `docs/design/semantic_ingestion_architecture.md` remain authoritative. A learned relation can describe semantic knowledge only when its domain policy permits it. User preferences, episodes, execution state, and solver observations need their own domain contracts. A model's fluent proposal is neither a catalog version nor a fact.

The base corpus must include at-home scenarios for household membership, household chores, appointments, bills and subscriptions, purchases and warranties, travel, home maintenance, personal preferences, pet care, and caregiving. In the initial home journey, an agent such as Hermes or OpenClaw runs for one signed-in PC/Mac account and reads that account's local logs. `Household` names a group in that user's facts; it is not a shared memory principal or an access-control list. Home facts use the authenticated user's existing fact scope, and another signed-in user cannot read them merely by being described as a household member. The corpus must prove user-scope isolation and correction or expiry where a fact changes. The [base catalog contract](learned_ontology_base_catalog.md) defines the closed `Preference` user-context record, confirmation and correction lifecycle, identity, and protected read. An agent's mention of a preference does not become a committed semantic edge. The same contract defines the only symmetric family read views; no reverse fact is written. Private financial and family facts remain scoped to authorized readers. A catalog relation being available never bypasses source, domain, or lifecycle validation.

This list is the default shipping floor, not a permanent ceiling. The [base catalog contract](learned_ontology_base_catalog.md) binds all 53 semantic relation IDs to type, scope, evidence, lifecycle, and read policies and identifies the new type/value capabilities they require. Those bindings are specified, not implemented; a relation cannot be counted as shipped merely because its label appears here. Ontology learning extends this base when evidence reveals a genuinely missing concept or relation.

## 4. Supported learned edit language

The shipped base above is available without a learning operation. The initial learned edit language accepts exactly one of two operations per proposal: `add_relation` or `add_entity_type`. `add_relation` has a new stable identifier in a scope-owned catalog and a closed declaration containing:

| Field | Required meaning |
| --- | --- |
| `relation_id` | Unique semantic identity; existing IDs cannot be redefined or aliased silently |
| `description` | Plain-language meaning used by proposal and evaluation; cannot be executable code |
| `subject_type` | Registered entity type with independent identity evidence |
| `object_kind`, `object_type` | Registered entity or literal type; canonicalization and domain validator must exist |
| `value_policy_id` | Required for a literal object; references a registered, versioned codec and, for `StatusText`, a relation-specific closed vocabulary and alias set. Forbidden for entity objects |
| `memory_domain` | Exactly one registered domain; initial slice permits semantic only |
| `catalog_authority_scope`, `fact_scope` | Catalog ownership and fact memory scope are distinct typed coordinates. The scope owner may activate only within its grant; fact scope uses the governing memory-domain enum and protected retrieval filters. Narrower evidence cannot authorize wider activation |
| `cardinality`, `correction_policy` | Registered, compatible multi-value, single-current, or historical semantics with explicit correction/retraction history |
| `temporal_policy`, `trust_policy` | Registered rules for event and valid time and source authority |
| `evidence_rule` | Exact source assertion, role, polarity, commitment, and provenance checks; unknown rule rejects |
| `read_behavior` | Protected lookup representation and historical-version behavior |
| `read_derivation_policy` | Registered `none` or `symmetric_view`; the latter is allowed only for a symmetric entity relation, creates no reverse fact, preserves the source assertion and version, and requires both endpoint visibility grants before an inverse result or count |

`add_entity_type` declares one new subtype of exactly one registered parent entity type. Its closed fields are `type_id`, `parent_type_id`, `description`, bounded aliases, `identity_policy_id`, allowed fact-scope class, and evidence rule. It inherits the parent's object representation and compatible validator/writer/reader capability; it cannot create a new top-level root, literal codec, memory domain, or identity algorithm. A new subtype must have independent source-grounded distinguishing evidence and a registered identity policy. A truly new root kind or one needing a new codec becomes `unsupported_capability` with retained evidence and an explicit future capability decision; it is never silently coerced to an unrelated parent.

Accepted values in either edit are references to versioned, built-in validator and policy capabilities. Candidate data cannot contain Python, expressions, prompt fragments interpreted as authority, network callbacks, or an arbitrary class name. One edit may use only capabilities whose validator, writer, and protected reader are already implemented and registered. If no such capability covers the proposed meaning, the candidate is retained as `unsupported_capability`; implementation of that capability is a separate design and implementation operation.

`rename_relation`, `change_relation`, `delete_relation`, `merge_relation`, root entity-type creation, and edits to existing type declarations are outside the initial edit language. Cross-scope promotion has a separate authorization and disclosure decision. Activation policy is selected by the scope owner and is not encoded by the edit language. Unknown operation kinds and unknown enum values fail closed. A later edit language needs a new protocol version and compatibility contract; it cannot reinterpret this one.

The base entity registry is a sorted, content-addressed sequence of the twenty canonical type IDs in Section 3 plus seven explicit subtype declarations: `Household -> Group`, `Appointment -> Event`, `Chore -> WorkItem`, `Subscription -> Agreement`, `Bill -> Obligation`, `Vehicle -> Asset`, and `Recipe -> Document`. Every declaration has a stable ID, optional single parent, description, allowed alias set, identity-policy ID, and scope class. Root IDs have no parent; aliases are normalized by a versioned Unicode normalization/case-fold policy before duplicate checks, but display spelling is retained separately. An alias may resolve to exactly one type within an effective catalog; collision with any ID or alias rejects. The parent graph must be acyclic, with one path to a root; inherited compatibility is transitive but does not authorize a subtype where only a different sibling is permitted. A persisted fact retains the selected type-registry digest. Reclassification of an existing entity or type ID is a separate migration, never an `add_entity_type` side effect. Unknown fields, multiple parents, alias cycles/collisions, duplicate IDs, unknown identity policies, and missing parent versions fail closed.

## 5. Learning mechanics and confidence

### Continuous coverage monitoring

The monitor records each eligible source and its downstream trajectory under a pinned catalog version: whether semantic extraction accepted, abstained, or rejected; which relation or policy caused a rejection; whether protected recall found a matching committed fact; and whether an authorized user later corrected a memory. It also records explicit schema-gap reports from an adapter as untrusted hints. A durable, scoped `CoverageObservation` carries source digest and span when available, core-derived origin-lineage and session IDs, agent and principal IDs, observation time, active catalog digest, observer/model/prompt versions when used, a closed semantic outcome (`covered`, `unsupported_relation`, `unsupported_entity_type`, `uncertain`, `ineligible`, or `not_evaluated`), a separate closed discovery-processing state, and the downstream failure signature. The processing states are `discovery_pending_no_capability`, `queued`, `running`, `classified`, `discovery_unavailable`, and `ineligible`. Source admission records `discovery_pending_no_capability` with semantic outcome `not_evaluated` when no authorized observer binding exists, otherwise `queued` with `not_evaluated`. Only `queued -> running -> classified|discovery_unavailable` may execute classification; `discovery_pending_no_capability -> queued` requires a newly authorized capability, and `discovery_unavailable -> queued` retries the same binding after recovery. `ineligible` and `classified` are terminal for that observation. A changed catalog or observer version creates a new observation identity, preserving the prior result. The idempotency key is `(source_id, source digest, catalog digest, observer binding version or none)`; retries cannot create duplicate observations, candidates, or facts. A public status projection returns `discovery_pending_no_capability` or `discovery_unavailable` directly from the durable processing state without treating `not_evaluated` as a verified gap. Restart reconstructs the queue from durable states; a recovered `running` attempt becomes `queued` under the same binding and attempt fence, with no candidate unless classification and recurrence later succeed. These signals are diagnostic, not facts. They let the monitor identify recurring gaps without requiring Memorii to possess an API key.

For each recurring failure signature, the learner first attributes the problem to one owner: `source_or_provenance`, `fact_extraction`, `catalog_coverage`, `protected_retrieval`, or `agent_exposure`. A rejected assertion due to an existing relation's extraction error is not a new ontology relation; a successful commit followed by a recall miss is a retrieval or exposure problem. Only verified `catalog_coverage` failures enter the schema proposal path. This adapts the diagnosis and single-layer intervention in [EvoOntology](https://arxiv.org/html/2609.15779v1#S3.S3) to Memorii's separate memory domains and owners. An inconclusive attribution remains `uncertain` for review rather than becoming a schema edit.

Before counting a gap, core resolves registered relations, types, aliases, and parent/child compatibility. It also diagnoses extraction failure, missing entity identity, retrieval failure, untrusted or quoted text, and ambiguous subject/object roles. Only a verified `unsupported_relation` or `unsupported_entity_type` enters recurrence tracking. Relation observations are grouped by normalized relation meaning, ordered endpoint types, direction, domain, and evidence rule; type observations by proposed parent, distinguishing identity evidence, and scope class. Text similarity may suggest a group, but a model cannot merge two signatures by itself. A validator must establish that grouped examples express the same relation or subtype; a contrary example splits or marks the group ambiguous. Count only core-verified independent origin lineages, not transcript copies, assistant repetitions, chunk windows, delegated-agent restatements, or adapter-claimed distinct IDs. Track first/last seen, independent lineage count, distinct session count, example diversity, and covered/uncertain counterexamples. No raw source crosses its disclosure boundary for grouping or review.

A group becomes eligible for a proposal after **three independent origin lineages in at least two sessions** under the same authorized catalog scope. This is a recurrence trigger, not a truth or confidence claim. A scope owner can request review of a single explicit gap, but one mention alone cannot auto-activate a relation. Coalescing uses a stable key from scope, parent catalog digest, semantic signature, and evidence lineages; new observations update the group rather than generating repeated proposals. The observer revisits unresolved groups when new evidence or a catalog version appears. Rejected groups retain reasons so the same unsupported wording does not cause an unbounded proposal loop.

### Discovery model and candidate construction

The learner requests a typed `ontology_observe` or `ontology_propose` capability through a provider-neutral core boundary. A deployment can bind that capability to a model already available through its agent host, a local model, or a separately configured remote provider. Memorii does **not** require an OpenAI API key or an OpenAI-hosted model for ontology learning. A host-supplied model response has the same untrusted status as any other provider response: core verifies exact evidence spans, scope, typed declarations, and paired evaluation. The host cannot grant catalog authority. The binding records provider, model and prompt identity, transport, privacy/egress policy, and compatible output schema; the evaluation gate is run for that exact binding. A different model may produce a different candidate, but the committed catalog's semantic identity and rules are provider-independent.

An optional remote reference profile could use pinned `gpt-5.4-mini-2026-03-17` for high-volume classification and pinned `gpt-5.4-2026-03-05` for grouped synthesis, if the deployment explicitly configures and authorizes it. These snapshots and structured-output support are documented in [OpenAI's Mini model reference](https://developers.openai.com/api/docs/models/gpt-5.4-mini) and [GPT-5.4 model reference](https://developers.openai.com/api/docs/models/gpt-5.4). [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) constrains shape, not semantic correctness. The existing `gpt-4.1-nano` fact extractor is a separate installed example, not an ontology requirement. With no ontology model capability, the shipped base catalog, deterministic source retention, protected recall of existing facts, explicitly structured fact proposals through the normal validator, and manual catalog review must remain usable; raw free-text discovery and synthesis stay pending until a capability is supplied. No silent remote fallback or secret lookup is permitted. A deployment whose free-text fact extractor also needs a model must bind one separately; ontology unavailability does not block an independently configured fact path. The current installed profile's model dependence is a baseline limitation, not a promise that it already meets this no-key requirement.

The synthesis input is bounded to authorized, provenance-verified examples, nearby existing definitions, and de-identified rejection reasons allowed in that scope. It must return one `add_relation`, one `add_entity_type`, or `no_new_schema`, plus exact support spans, counterexamples, alias/overlap analysis, registered capability references, and a predicted behavioral effect. A relation edit also supplies endpoint types and direction; a type edit supplies one registered parent and identity policy. It cannot add capabilities, write prompts or code into the catalog, choose a broader scope, or score its own correctness. A deterministic parser and domain validator either build the typed candidate or record a rejection. Separate prompt/model manifests and content digests make a model update an explicit re-evaluation event without changing an already activated catalog's meaning. A scope-authorized owner may submit the same typed candidate manually when no model is available; that route passes identical validation and evaluation.

### No-key structured fact boundary

The no-key base-fact path is a separate authenticated `submit_structured_fact` core entry point, composed beside source admission at the generic provider root and available to any conforming host adapter. Its closed envelope contains the already retained `source_id` and source digest, authenticated delivery principal and agent binding, source/fact scopes and grants, exact retained-source segment/span references, the core-selected effective catalog-owner coordinate and catalog digest, one typed `ProviderSemanticProposal` (or its versioned successor), and a content digest of the raw host proposal artifact plus its provider/model/prompt provenance when applicable. Core, not the adapter, resolves and pins the catalog before accepting the proposal; a caller-supplied digest is only an expected-value assertion and rejects on mismatch. Core canonicalizes the immutable operation envelope `(source_id, source digest, source scope, sorted exact retained-source segment/span references, authenticated principal and agent, fact scope, catalog-owner coordinate and digest, raw proposal artifact digest, provider/model/prompt provenance digest or none, structured-proposal protocol and parser version)` and derives `structured_operation_id` from its domain-separated digest. It persists that ID **and** the canonical envelope digest before proposal validation or writer entry; the caller cannot choose the ID. A repeated ID with different immutable envelope bytes rejects as an identity mismatch. Current grant state is not part of the identity and is rechecked at the commit fence. Returning an existing terminal result also requires the caller's current read/status grant; a revoked caller receives a denied response without changing the stored terminal result or exposing fact content. The same authenticated envelope on a retry or after restart resumes the same terminal operation and fact/event dedupe identity; a distinct raw proposal digest or exact source span from the same retained source is a distinct operation requiring independent validation. Concurrent delivery of one identity can commit at most one fact/event set. The proposal is untrusted even when produced by a host model or a user form. It enters the existing transport parser, source quotation/role checks, domain-semantic validator, trust/temporal/lifecycle policy, and transactional writer in that order. Source retention and operation pinning precede proposal acceptance; retries use the same canonical envelope. A missing or revoked source grant, absent raw artifact, conflicting agent identity, wrong scope, stale catalog, or invalid proposal yields a durable non-committing outcome. Admission-time authorization is insufficient: the writer must apply the current-grant commit fence defined in Section 8 before any durable fact/event write. This port has no credential resolver and performs no network call. A deployment with neither a model nor a structured proposal can retain sources and read existing memory but cannot extract new facts from arbitrary free text; its status must say so.

### What confidence means and when a relation becomes first class

`ontology_confidence` estimates **whether this proposed relation or subtype is distinct, reusable, and reliably extractable under its declared evidence rule in this scope**. It does not estimate whether a particular source assertion is true. Do not use the model's self-reported confidence or agreement between two prompts as this score. A separately versioned calibrator uses labeled proposal outcomes and features such as independent lineage count, role agreement, alias separation, contradictory examples, and held-out extraction/abstention results. Labels come from scope-authorized reviewers who inspect grounded evidence and from later adjudicated errors; source examples used to build a proposal cannot label or test it. Training and calibration use only data whose grants permit that use. Record calibration dataset identity, model version, domain/scope cohort, reliability results, and drift checks. An uncalibrated or out-of-distribution proposal has `confidence_unavailable`, not a fabricated number.

The corpus is partitioned by origin lineage and near-duplicate source family into disjoint development, frozen paired-acceptance, calibration, and final-audit sets before candidate tuning. Raw source text or labels cannot cross scope grants merely to enlarge a cohort. For the owner-enabled automatic policy, evaluate the separately fitted calibrator on independently adjudicated candidates in the untouched calibration set for the exact edit kind, provider, prompt, domain, and scope cohort. Among candidates scoring at least 0.95, require at least 59 eligible labels and a one-sided exact Clopper-Pearson 95% lower bound on valid-proposal precision of at least 0.95; 59 flawless labels meet that bound, while any errors require more evidence. A binding change, drift, sparse cohort, or scope mismatch makes confidence unavailable. Post-activation audits inform only later calibrator versions. These are design thresholds, not evidence that a current model reaches them.

Promotion is governed by all of these gates, in order:

1. **Candidate:** recurrence trigger or explicit owner request opens a proposal. It remains inert while evidence, typed policy, and evaluation are checked.
2. **Validated:** every source span and scope grant verifies; no existing relation, type, or alias covers the meaning; registered validators, writer, and protected reader support it; and the withheld positive, negative, correction, scope, and parent-regression cases in Section 7 pass. Any failed mandatory case blocks promotion regardless of score.
3. **Agent-local first class:** the authorized owner may explicitly accept a validated candidate for one closed `CatalogAuthorityScope` agent overlay defined in Section 6. This is an auditable judgment, not a claim of 95% statistical certainty. Alternatively, an owner-enabled automatic policy may accept only when there are at least three independent lineages across two sessions, `ontology_confidence >= 0.95`, and the held-out calibration cohort for scores at or above 0.95 has a one-sided 95% lower confidence bound on precision of at least 0.95. If the cohort lacks enough labeled candidates, the calibration is stale, or the proposal is outside its validated domain/scope cohort, automatic acceptance is disabled and owner review is required. A score can never waive a mandatory validation failure.
4. **Active:** acceptance publishes an immutable version and atomically selects it for that agent-local scope. Only then is the relation or subtype first class for future fact extraction and protected recall by that agent under both fact-scope and catalog-owner grants. Existing facts are not reinterpreted; retained eligible sources may be replayed through normal ingestion. Other agents, users, tenants, and the shared base do not inherit it. Wider promotion needs a new disclosure authorization, independent evidence/evaluation, and an owner decision; no confidence threshold alone grants wider authority.

This 0.95 rule is a **proposed policy target**, not a measured property of the current system. Automatic activation stays off until labeled calibration and its precision bound demonstrate the target for the actual provider, prompt, and domain cohort. Reviewer-approved activation can still serve sparse agent-local use cases, with the decision and limitations visible in status. If post-activation adjudication finds aliasing, bad extraction, or scope leakage, the owner can select the prior catalog version for future work; prior records and evidence remain auditable.

### What is adopted from EvoOntology

[EvoOntology](https://arxiv.org/html/2609.15779v1) constructs evidence-grounded ontology entries, then uses trajectory attribution, localized typed edits, and paired validation before retaining an edit. Memorii adopts those mechanics for **schema coverage**: use source and runtime traces together; classify the failing owner before changing anything; propose one typed relation; retain source references and rejection history; compare the candidate with its exact parent under the same model binding and budget. A reference to a source span is analogous to EvoOntology's grounding probe, but transcript evidence cannot prove fact truth or source authority. Memorii's memory-domain validators and grants remain independent of the paper's data-agent architecture. Its Content, Tool, and Schema layers are not copied into Memorii's distinct semantic, episodic, execution, solver, and user-context stores. EvoOntology's observed gains on data-agent benchmarks are motivation for this method, not evidence that Memorii's proposed thresholds or models work.

## 6. Candidate, evaluation, and activation authority

`CatalogAuthorityScope` is a closed, versioned discriminated coordinate distinct from fact `MemoryScope`:

| Variant | Required fields | Parent selection |
| --- | --- | --- |
| `base` | No tenant, user, or agent ID | None |
| `namespace` | `namespace_kind: personal|tenant`, stable `namespace_id` | `base` |
| `tenant_user` | `tenant_id`, authenticated `user_id` | `namespace(tenant, tenant_id)` |
| `agent` | `namespace_kind`, `namespace_id`, authenticated `agent_id`, optional authenticated `user_id` only for a tenant namespace | `tenant_user` when user ID is present; otherwise the named `namespace` |

A personal namespace ID is the authenticated personal user's stable ID; a tenant namespace ID is its authenticated tenant ID. A user-specific agent has one exact parent chain `agent -> tenant_user -> namespace -> base`; a tenant agent has `agent -> namespace -> base`; a personal agent has `agent -> personal namespace -> base`. A user-specific request never silently selects a tenant-agent overlay. A request without a verified agent ID cannot select an agent overlay. Core derives tenant, user, and agent fields from authenticated principal/host bindings rather than source text, proposal output, or a caller-chosen display name. It rejects mismatched, absent, or ambiguous bindings, including the same agent ID claimed under another namespace. The serialized coordinate is a tagged canonical tuple with exact fields per variant; unknown variants and extra/missing fields reject. Pointer keys and proposal/version/activation records carry this exact coordinate, not an untyped scope string.

The packaged `base` is changed only by product release authority. A tenant administrator controls its tenant namespace; an authenticated user controls a personal namespace or tenant-user overlay only within grants delegated by the tenant; an agent overlay is controlled by that namespace/user owner or an explicitly delegated catalog grant bound to the same agent identity. Only an agent overlay may enable the calibrated automatic policy in this initial design. An observation from a narrower source never grants authority to activate a parent catalog. Catalog activation grants are separate from fact-scope grants, and both are checked at activation and read time.

Lookup starts at the most specific coordinate for which the caller has an authenticated binding and an active pointer, then follows that coordinate's one parent chain. Each published version is a **complete immutable effective catalog** with a digest of its exact parent version, not an unordered union of current overlays. If the child pointer is active, a later parent update does not silently alter its meaning; the child stays pinned to the parent digest recorded at publication until an authorized rebase is validated and selected. A missing/invalid child pointer fails closed for that child instead of falling back to a broader catalog; absence of a child pointer permits explicit parent selection. A retired required capability makes the affected version unavailable until revalidated. In-flight work pins the selected effective version before proposal egress; replay keeps its recorded owner coordinate and catalog digest and rechecks current grants. No cross-agent or cross-tenant replay is inferred from matching source text.

Every committed fact records both its ordinary fact scope and the `CatalogAuthorityScope`/catalog digest that authorized its relation or type. A protected read must satisfy both gates: the caller's current fact-scope grant and visibility to that catalog-owner coordinate. An agent-local fact is visible only to the same authenticated agent binding and authorized user/tenant principal, even when another agent has the same ordinary user or tenant fact-scope grant. A fact created under a broader parent catalog follows that parent's visibility policy. Historical reads resolve the stored owner and digest; rollback and later wider catalog promotion do not widen earlier agent-local facts. Making those facts visible more widely requires a separately authorized, evidence-preserving replay through the wider catalog and normal writer. This rule is enforced before relation rendering, search snippets, or result counts can disclose the agent-local fact.

For the initial home catalog, the signed-in account's authenticated `user_id` remains the fact-scope owner. A `Household` entity, `member_of` claim, relationship edge, or shared-chore wording cannot grant another person's account access. The design introduces no household or tenant-group fact-visibility scope and no membership-derived read grant. A future multi-account household feature would require a separate change to the governing fact-scope and authorization contracts; it is outside this ontology design. Organizational tenant catalog ownership similarly does not create a new tenant-shared private fact scope: such facts use only an independently authorized existing fact scope and grants.

The core owns four typed records. Names are behavioral proposals, subject to the WorkPlan identity review before approval.

| Record | Contents and authority |
| --- | --- |
| `OntologyEvidenceReference` | Source ID, retained artifact digest, source/fact scope, authenticated author/agent grant, core-verified origin lineage, exact span, observed time, and closed gap classification; it carries no fact truth |
| `OntologyChangeProposal` | Stable proposal ID, parent catalog digest, exactly one typed edit, evidence references, proposing principal, exact `CatalogAuthorityScope`, creation time, closed lifecycle state, validation/evaluation/decision result references when reached, and last activation attempt/result; model output may fill candidate fields only |
| `OntologyCatalogVersion` | Immutable sorted type and relation declarations, exact parent digest, schema version, validation/evaluation result digests, `CatalogAuthorityScope`, publication time, and content digest |
| `OntologyActivation` | Exact `CatalogAuthorityScope`, closed operation kind `activate_candidate|select_prior_version`, activation-attempt ID, candidate proposal ID only for activation or verified prior target digest only for rollback, expected pointer digest/sequence, selected catalog digest, authorizing principal/grant or enabled policy, decision time, proposed next sequence, and closed `prepared|selected|abandoned` attempt state |

The proposal state enum is closed. The complete allowed transition inventory is: `draft -> validating`; `validating -> validated|validation_unavailable|rejected`; `validation_unavailable -> validating`; `validated -> evaluating`; `evaluating -> evaluated|evaluation_unavailable|rejected`; `evaluation_unavailable -> evaluating`; `evaluated -> awaiting_decision`; `awaiting_decision -> approved_for_activation|rejected`; `approved_for_activation -> active|activation_conflict`; and no outgoing transition from `rejected`, `active`, or `activation_conflict`. A stale-parent conflict cannot retry selection or silently use the new parent; a rebase creates a new proposal identity and repeats validation and evaluation. Unavailable validation/evaluation may retry only against the same parent, catalog, provider/prompt binding, frozen cases, and budget; deterministic failure is `rejected`. Each state transition is an idempotent durable event keyed by proposal ID, previous state, transition kind, and input/result digest. The proposal projection records the current state, exact validation and evaluation result digests, decision actor or policy and evidence digest, activation attempt ID, expected pointer digest, and selected version/sequence when active. Recovery reconstructs state from durable events, verifies referenced artifacts, and resumes only the permitted next transition; it never reruns an approved evaluation under a changed binding. Duplicate requests with the same parent, edit, scope, and source lineage coalesce; a changed meaning receives a distinct proposal ID. A rejected proposal and its reasons remain visible to authorized reviewers.

The wire grammar is closed and versioned. The initial protocol version has exactly one `add_relation` or `add_entity_type` edit per proposal, exactly one parent catalog digest, one `CatalogAuthorityScope`, one proposing principal, one to eight distinct core-verified origin-lineage references, and one typed declaration matching the edit. Arrays have canonical order and no duplicate IDs; text is bounded UTF-8; digests use the repository's typed canonical-value digest helper with distinct domains for proposal, catalog, type registry, evaluation, and activation. Persisted records use explicit schema version and reject unknown keys and enum values. The active pointer contains only a canonical `CatalogAuthorityScope`, activation sequence, selected catalog digest, and selected activation-attempt ID; it never stores a mutable declaration body. Requirement and WorkPlan IDs are permitted only in separate typed traceability records, never in these persisted identities.

Canonical learned relation IDs are 1 to 64 ASCII bytes matching `[a-z][a-z0-9]*(?:_[a-z0-9]+)*`; canonical learned subtype IDs are 1 to 64 ASCII bytes matching `[A-Z][A-Za-z0-9]*`. These IDs are exact-case protocol tokens: core does not trim, Unicode-normalize, or case-fold them, and rejects non-ASCII, whitespace, alternate separators, leading/trailing/doubled underscores, and case variants instead of silently changing bytes. `unknown`, `none`, `null`, `base`, `agent`, `namespace`, and `tenant_user` are reserved in their corresponding case forms, as are all built-in type/relation IDs and normalized aliases in the effective catalog. Alias text alone uses the separate versioned Unicode normalization/case-fold rule in the type registry. Collision checking uses exact canonical ID bytes, an ASCII-casefold index for type IDs, and the normalized alias index across the complete parent catalog and proposed edit; a changed capitalization or non-ASCII confusable cannot create a second ID. Core derives `proposal_id` as `ocp_` followed by 64 lowercase hexadecimal characters from a domain-separated SHA-256 of the typed canonical tuple `(protocol version, catalog-owner coordinate, parent catalog digest, edit kind, complete canonical edit bytes)`. The caller cannot set it. Equal tuples coalesce under that ID; additional evidence for the same gap updates its observation group but does not mutate the frozen proposal record. Different edit bytes create a new proposal and require evaluation. The parser and identity-hygiene gate mutate each accepted form with wrong case, Unicode, separator, reserved word, length, alias collision, and a forged proposal ID to prove rejection.

The scope owner's grant authorizes only its catalog scope. A model, adapter, delegated agent, or source text cannot assert activation authority by its own output. The active pointer is governed state, not a field inferred from the newest catalog file. Publication and selection are separate durable steps: an orphaned immutable version is safe; a pointer to a missing or unverified version is invalid and must stop new ingestion for that scope. Recovery checks the pointer and its selected catalog before issuing any proposal request.

The catalog-selection API accepts exactly one operation kind. `activate_candidate` receives the authenticated catalog-owner scope, activation grant or owner-enabled automatic-policy identity, expected pointer digest/sequence, approved candidate digest and proposal ID, and explicit decision; it publishes a new immutable version before selection. `select_prior_version` receives the same authenticated scope and catalog-selection grant, expected pointer digest/sequence, exact target catalog digest, and explicit rollback reason. Its target must have appeared in an earlier **selected pointer attempt in the same catalog-owner scope** and be an ancestor of the current effective catalog version's verified parent chain. The registry verifies that historical selected attempt, immutable target bytes, parent chain, and read capabilities; an orphaned publication, merely prepared or abandoned attempt, activation-conflict version, other-scope version, or sibling branch is ineligible even if its bytes verify. The packaged seed is installed with a verified genesis selected-pointer record in its scope, so it can be a legitimate prior target. Rollback does not create a candidate, republish a version, or transition the old proposal state. Both kinds reject extra kind-specific fields and require current authorization before preparing an attempt or changing the pointer. A rejected or pending candidate remains inert. Integration-specific configuration may authorize source delivery, but it cannot substitute for catalog activation authority. Installing files or changing a model environment variable is never an activation operation. The activation attempt and pointer are persisted in the scope's catalog store and verified on startup.

For `activate_candidate`, the catalog store appends a complete immutable version before attempting pointer selection; `select_prior_version` verifies and reuses already published immutable bytes. Under a lock for the catalog-owner scope, the selection owner rereads and verifies the expected pointer and writes one `prepared` attempt keyed by `(operation kind, catalog-owner coordinate, proposal ID or rollback target digest, expected pointer digest and sequence, selected catalog digest, authorizing decision digest)`. Its attempt ID and proposed next sequence are deterministic for that tuple; repeated preparation returns the same record. Only the successful durable pointer compare-and-swap selects the version, sequence, and attempt ID. The attempt then becomes `selected`; only candidate activation changes its proposal to `active`, while rollback leaves both old proposals unchanged. Success is reported only after selected-state finalization. If interrupted after preparation but before pointer selection, startup keeps the prior pointer active and may retry that exact prepared attempt only while its expected pointer still matches; otherwise it marks the attempt `abandoned` and records a conflict for that attempt. A candidate activation also moves its proposal to `activation_conflict`, requiring a new rebased proposal. If interrupted after pointer selection but before the attempt's selected-state projection is written, startup verifies the pointer's attempt ID, immutable version, and authorizing decision, then idempotently finalizes `selected` and, only for a candidate activation, `active`. A prepared record alone is never shown as activation or rollback. Only selected pointers consume a monotonic activation sequence; an abandoned attempt cannot reserve one. A pointer with a missing record or catalog is an integrity error, not permission to select the newest available file. Existing fact/event persistence remains owned by the semantic writer; catalog selection cannot write a graph delta. Crash tests cover version append where applicable, prepared attempt flush, pointer CAS, selected-state flush, restart, repeated activation or rollback, and concurrent activation versus rollback.

Evidence from delegated subagents that traces to one original source counts as one lineage. A private or tenant-scoped source cannot be disclosed in a broader proposal or used to activate a broader catalog. Every candidate uses evidence authorized for its catalog-owner scope; promotion to a wider scope requires a separate authorized disclosure and evaluation decision.

## 7. Validation and evaluation

Validation is staged:

1. Parse a closed typed proposal; reject extra fields, unknown operation or policy values, malformed IDs, excessive size, and duplicate entries.
2. Verify every evidence reference against retained source bytes, source scope, author/grant, and common origin lineage. Exact quotation is necessary but not sufficient for asserted meaning.
3. Check the proposed edit against the parent catalog: no identifier, alias, or normalized-name collision; no mutation of an existing declaration; all referenced capabilities, types, identity policies, and literal value policies registered in the current runtime. For a subtype, check the single-parent graph for cycles and incompatible sibling or alias reuse.
4. For a relation, check independent subject/object role evidence, polarity, commitment, temporal and correction behavior, domain routing, scope, and protected-read support. For a subtype, check distinguishing type evidence, parent-compatible identity, and protected subtype reads. The edit must be representable by registered capabilities without special-case model authority.
5. Compare the candidate with the parent on the same source fixtures, model or structured-proposal binding, decoding and interaction budget, and read tasks. Freeze the targeted gap cases and the acceptance margin before running either version. An added relation must correctly commit and retrieve at least two withheld targeted positive cases the parent cannot represent. An added subtype must correctly distinguish and retrieve at least two withheld subtype identity cases that the parent can represent only as the broader type, without splitting same-entity aliases. Both edit kinds must reject withheld unsupported or misleading examples and preserve the parent catalog's registered behavior. Any authorization, provenance, scope, or data-integrity failure rejects regardless of answer score. Record paired case results and provider identity; do not treat the model result as semantic proof. A different fact-extraction provider requires its own paired result before that provider can use the learned edit.
6. Present the validated candidate, evaluation difference, evidence provenance, confidence availability, and limitations to the scope-authorized owner or the owner-enabled automatic policy for a recorded accept/reject decision.

The evaluation set must include direct assertion or subtype identification, negative/quoted/reported/hypothetical wording, ambiguous role assignment, correction, and protected read for the proposed edit, plus regression cases for existing relations and types in the parent catalog. Sources used to generate a candidate cannot serve as withheld evaluation cases; source lineages and near-duplicate wording stay in one split. Candidate generation, paired acceptance, calibration, and final audit use distinct source-lineage partitions. Activation requires every scope/provenance/integrity negative to reject, every parent-catalog regression to preserve its expected result, at least two withheld targeted positive sources to commit and read correctly, and all withheld unsupported or misleading sources to abstain. It also requires a positive paired gain on the predeclared targeted cases under the same budget. A missing required case, timeout, model error, or inconclusive outcome records `evaluation_unavailable` with no activation. Neither an activation owner nor an automatic policy can waive a failed safety or integrity check. This per-candidate gate is distinct from the population calibration evidence required for automatic activation. The paired and separated evaluation follows the causal comparison in [EvoOntology](https://arxiv.org/html/2609.15779v1); its results cannot be transferred to a different model binding by assumption.

## 8. Production binding and version semantics

Every agent integration submits source through a shared core admission contract carrying authenticated principal, source scope, core-derived origin lineage, provenance, and permitted memory domains. Before semantic processing, core resolves the active catalog for the exact authorized `CatalogAuthorityScope` and verifies its content, parent, scope, and capabilities. The selected catalog digest joins the source/proposal authority. The request materializer supplies the selected `PredicateProposalCatalog` and matching semantic trust, temporal, state, routing, and adapter-semantic bindings. The provider binding separately verifies model, endpoint, transport, prompt/output-schema compatibility, credentials, and egress policy. A prompt or model change cannot silently change the catalog's meaning, and a catalog change does not authorize a new provider binding. A packaged seed may be retained as a rollback target, but it has no special authority over later catalogs. Catalog ownership does not add values to the closed `MemoryObject.scope` enum; committed facts retain their domain's canonical fact scope **and** catalog-owner visibility binding, both enforced by protected retrieval.

The owner-to-owner path is:

| Trigger | Caller and arguments | Owner and outcome | Absence behavior |
| --- | --- | --- | --- |
| Source admission | Any authorized adapter supplies authenticated principal, scope, provenance, claimed origin, source, and grant | Core derives origin lineage, retains source, and monitor records deterministic outcomes; an available semantic observer may classify a grounded gap separately from fact ingestion | With no ontology model, raw-text classification remains visibly pending; source and existing memory remain available |
| Structured fact submission | Authenticated host supplies retained source reference, proposal bytes/digest, scope/grants, agent binding, and expected catalog digest | Core resolves/pins catalog, derives and persists `structured_operation_id`, and runs transport, semantic, provenance, lifecycle, and writer checks for the untrusted proposal | Missing key is irrelevant; missing source/grant/catalog or invalid proposal gives a durable non-committing result; retry returns its prior terminal outcome |
| Candidate preparation | Core learner after verified recurrence, or authorized manual proposer, supplies scoped evidence references and expected parent catalog digest | Catalog validator creates one typed relation or subtype candidate with closed declaration and evaluation result | Invalid or unsupported candidate is rejected with reason; a missing model leaves automated synthesis pending |
| Catalog selection | Scope-authorized owner supplies `activate_candidate` with approved candidate or `select_prior_version` with verified same-scope rollback target, grant, and expected pointer identity | Registry prepares a kind-specific attempt and compares/swaps active pointer; only candidate activation publishes a version or changes proposal state | Missing grant, stale pointer, missing bytes, or failed check leaves old pointer active; retry uses the same attempt identity |
| New ingestion or retry | Core semantic authority receives selected catalog digest and verified version from the registry | Materializer, semantic policies, adapter, and provider compatibility binding use one pinned catalog identity | Inconsistent or unavailable version blocks semantic promotion; no fallback to newest file |
| Replay after activation | Replay scheduler receives selected version, eligible source refs, and current grants | Existing source preparation and graph transaction path runs with fresh replay operation identity | Revoked source is skipped with durable reason; retry uses same selected digest |
| Protected recall | Reader receives caller fact-scope grant and authenticated catalog-owner/agent binding plus the committed fact's owner coordinate and catalog digest | Reader verifies both visibility gates and the historical declaration before rendering or counting | Missing owner grant or historical declaration fails closed for that fact |

In the current Hermes-backed implementation, the installed package validator requires exactly three catalog entries; the output schema and adapter `_PREDICATES` enumerate the same three; the transport sends a fixed prompt/schema; the request materializer, trust/temporal policy, and state-rule builder repeat those IDs; and the local sidecar binds package digests. Those fixed assumptions are one implementation mapping to replace, not the general ontology architecture. The protected reader is already predicate-generic; it needs historical catalog identity and visibility checks, not a fourth-ID switch. A generated output schema may enumerate the selected catalog's permitted IDs, but it remains a provider-bound artifact whose compatibility with the semantic catalog is verified separately. It cannot define or change ontology meaning.

Downstream code inspection of the current Bootstrap V3 path found no further three-predicate allowlist in proposal normalization, source-normalization policy lookup, generic graph planning, claim compilation, or graph transaction dispatch. A `TEXT` relation such as `project_priority` has a representable literal object shape only if its upstream catalog, trust, temporal, state, provider, and identity bindings are complete. The installed root rejects it before the writer. This is a discriminating current-path finding and a design insertion map, not end-to-end proof; the implementation operation must run a fourth-relation assertion, abstention, revision, write, and protected-read test after those authorities are generated from the new catalog.

Source retention may complete while ontology processing is unavailable. Before a retained source first enters semantic processing, the worker durably pins the verified active catalog digest and `CatalogAuthorityScope` to that operation; pin persistence precedes provider proposal egress. Retries of that operation use the same identities. A response, validator, writer, and protected reader reject a mismatch between operation, proposal, policy, and catalog. New facts retain both catalog identities under which they were committed. Selecting a newer version changes future operations only. It does not rewrite, reinterpret, or delete prior facts. Protected reads may combine versions only through explicit compatible read mappings; in the initial additive edit language, unchanged declarations retain identity and new entries are absent from old versions. Current seed-profile fact projections do **not** carry a stable per-claim catalog digest, and the installed sidecar's current package digest is not per-fact migration evidence. Therefore no automatic seed-to-new-catalog mapping is authorized. Pre-catalog records remain readable only through a separately retained, verified legacy reader under their original fact grants; the new catalog reader must deny them until a future evidence-backed migration records an exact old-record-to-seed binding. Missing legacy reader is an explicit unavailable outcome, not a best-effort reinterpretation. This design decision removes any assumption that existing records can be inferred to belong to the new base.

Every initial provider, host-structured, and replay fact operation carries the source-grant and target fact-scope grant identity/version obtained at admission into the semantic writer. Immediately before its durable fact/event transaction commits, the writer calls the canonical authorization owner under a commit fence that serializes this check and the write against grant revocation or scope change. It verifies current source retention/disclosure and target fact-scope authority for the same authenticated principal, agent, source, and pinned catalog-owner coordinate; an admission snapshot alone cannot authorize a later commit. A revoked or changed grant aborts the transaction with a durable `authorization_revoked_before_commit` non-committing outcome, leaving no new fact or event. A revocation that wins the fence first blocks the write; a commit that wins first precedes revocation and remains governed by protected reads using current grants. This fence applies equally to fresh ingestion, `submit_structured_fact`, retry, and catalog-triggered replay. The implementation must use one authorization transaction or a grant-owner lease/lock spanning validation through fact commit; a separate read followed by an unfenced write does not satisfy this contract. Tests revoke or alter the grant between pinning and commit at each entry path and assert zero new committed records when revocation wins.

Rollback uses the closed `select_prior_version` operation to select a previously verified, same-scope immutable version for future operations through a new selection attempt and pointer CAS. It does not reactivate or rewrite the earlier proposal, append another catalog version, erase version history, or alter facts committed under the later version. Reads for facts from the later relation remain governed by that version's retained policy and scope even after rollback; if its read capability is unavailable, fail closed and report the unavailable relation rather than reinterpret it under the old catalog. Retry, crash recovery, and concurrent activation use the same expected-pointer and prepared-attempt rules as candidate selection.

After activation, a replay worker selects retained sources whose verified gap classification matches the added relation or subtype and whose current grant permits reconsideration. Replay creates a fresh operation identity from `source_id`, source digest, selected catalog-owner coordinate and digest, and replay reason, then uses the normal source preparation and semantic commit path. That identity binds the existing operation fence, transaction group, event dedupe key, and mutation digest; the catalog owner, digest, and policy reference are persisted in replay-authoritative payload, so recovery never infers them from the current active pointer. A repeated replay is idempotent under those existing identities. Revoked or deleted sources are skipped with a durable reason. Normal semantic validation may still abstain or reject. No catalog approval directly adds a graph edge.

The scope-authorized status surface reports active catalog digest, candidate counts and outcomes, activation sequence, replay backlog, and last error without disclosing source text. A missing catalog, invalid pointer, revoked grant, or capability mismatch blocks new semantic promotion and surfaces an error. Retained source recovery remains governed by core and its source adapter; errors do not become success-shaped empty facts.

## 9. Failure model and limits

The initial edit protocol caps each proposal at one relation or subtype, eight source references, and 4 KiB of human-readable description. An active catalog contains at most 512 relations, 128 entity types, and 2 MiB of canonical declaration bytes; the full 53-relation base fits without consuming nearly all extension capacity. Candidate evaluation is batched at up to 16 cases per invocation and at most 256 cases overall, with one model attempt per case and a 30-minute total wall-clock limit. A missing mandatory case or timeout leaves the candidate pending with no activation; the gate cannot quietly sample away a required parent regression. The separate, versioned calibration corpus may contain more labeled candidates and cases and is required before automatic activation. Replay processes at most 256 retained sources in one batch and leaves the rest durably queued. These are bounded protocol defaults subject to design review. Candidate validation and evaluation are retryable only for unavailable dependencies; deterministic semantic rejection is terminal. Version persistence is idempotent by digest. Pointer selection is a single compare-and-swap. A crash before pointer selection leaves the old version active; a crash after selection is recovered by reading and verifying the selected immutable version. Replaying one source twice cannot duplicate committed facts. Two concurrent candidates based on one parent cannot both activate without one rebasing and being reevaluated.

## 11. Alternatives and later scope

A larger manually packaged catalog remains useful for bootstrapping but does not learn. Letting the model invent a predicate in a fact proposal would conflate two validation lifecycles and cannot preserve historical meaning. An additive, typed, scope-authorized catalog is the initial learning contract. Future edit protocols may add relation changes and new capabilities. Delegated or bot-channel sources use this same contract once their independent identity and scope bindings are implemented; the ontology design does not reserve learning for a particular harness.
