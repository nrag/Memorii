## Verified Baseline And Problem

`api/service.py::MemoriiRuntimeAPI` receives four stores and `core/execution/service.py::RuntimeStepService.step` independently writes solver nodes, edges, overlay, generated events and a result. The supplied execution, solver, overlay and general event-log stores are all in-memory. `core/persistence/resume.py::ResumeService` reads those objects; `core/persistence/replay.py::ReplayService` reduces only some nodes/edges. Root creation is not emitted as a reconstructible execution event, and some solver commit events contain only IDs. Serializing the present event log would therefore still not restore complete state.

`core/directory/directory.py::MemoryDirectory` also owns process-local associations. `tests/unit/core/test_resume_service.py` and `tests/integration/test_harness_runtime_integration.py` prove same-store resume, not process restart. The focused baseline command passed eight tests; this is diagnostic confirmation of existing behavior, not durability proof.

Separately, `core/filesystem_storage/bundle.py::FilesystemStorageBundle` already persists semantic/provider memory, work state, decision state and traces. Their canonical records, authority and historical semantics must remain intact through the specified backend migration; auxiliary stores remain registered participants. Provider work-state IDs can reference solver/execution IDs without making the corresponding graphs durable. Hermes currently composes the provider path, not a durable `MemoriiRuntimeAPI`.

## Architecture And Ownership

Use a single physical `PartitionDataRepository` backed by SQLite WAL with full synchronous commits, with separate runtime and memory-plane domain views. This is a physical backend for several separate logical stores, not a single untyped memory model. Execution structure, solver structure, overlay versions, justifications, source references, task directory and operational records have separate closed schemas and reducers. The semantic/ontology owners retain their contracts while the new SQLite memory-plane backend replaces JSONL after verified cutover.

Planned ownership:

| Owner / path | Responsibility |
| --- | --- |
| `core/persistence/contracts.py` | Closed command, record, event-batch, checkpoint, receipt and revision schemas |
| `core/persistence/repository.py` | Backend protocol, unit of work, snapshot readers, commit/replay invariants |
| `stores/sqlite/partition.py`, `core/memory_plane/sqlite_store.py`, runtime repository view | Shared physical transactions plus domain-scoped stores; no reasoning policy or cross-domain grant |
| `core/persistence/replay.py` | Registered independent execution/solver/system reducers; canonical validation; no host logic |
| `core/persistence/resume.py` | Consistent authorized restoration, temporal checks and host reconciliation needs |
| `core/execution/service.py` | Computes validated candidate changes against one immutable revision; never mutates durable store views individually |
| `api/service.py`, `api/models.py` | Evolve existing API/results into explicit authenticated command/read methods |
| `core/harness_state/` | Bounded state views, recommendation contracts, cursor validation and deterministic text rendering |
| `core/storage_administration/` | Installation modes, participant barrier, backup/restore, export, forgetting and capacity operations |
| `core/filesystem_storage/bundle.py`, new `core/persistence/factory.py` | Compose backend-neutral memory owners and runtime views of the same selected partition; no JSONL/in-memory fallback after cutover |
| `integrations/` | Host-specific identity/lifecycle translation only |

SQLite is chosen over independent JSONL files because one transaction can enforce coupled graph/event/dedupe/receipt publication. A JSONL generation directory with an atomic root pointer is a viable alternative, but would require a second cross-file coordinator and custom indexes. Reusing the semantic graph store wholesale is rejected: its schema/authority/commit lifecycle is not execution or solver state. PostgreSQL is deferred because a local first release does not need network infrastructure. Backend registration uses entry point group `memorii.runtime_state_backends`, explicit `sqlite` selection, typed capability metadata and health; ambiguous/missing backend rejects startup.

Only repository-scoped store views are given to runtime owners. Durable mode prohibits independent public `upsert` and `append` paths. In-memory stores remain explicitly named test/ephemeral constructors. Public production roots require a persistent root and authenticated authority; optional absent dependencies return `unavailable`, never a memory-backed success.

## Shared Application Data Storage

The first release uses one `PartitionDataRepository` per physical isolation partition, backed by one SQLite WAL database with `synchronous=FULL`, foreign-key enforcement and a bounded busy timeout. A partition is an installation-owned storage unit, not a task ID or a model-supplied scope. The default installation has one partition; sharing it does not grant one principal access to another principal's records. Cross-partition transactions and transparent splitting/merging of existing installations are unsupported. The independent security/control database and key owner remain outside replaceable application-data generations.

`RuntimeStateRepository` is the runtime-owned view of this coordinator. A new `SqliteMemoryPlaneStore` implements the existing `MemoryPlaneStore` contract over the same data connection/transaction coordinator. `SemanticIngestionAtomicStore`, `MemoryPlaneService`, `LearnedRelationRuntime` and scoped catalog owners remain the only corresponding domain writers. They do not receive raw SQL access to other domains. `PartitionDataRepository` coordinates transactions, publication and snapshots; it does not plan memory, validate semantic truth, activate catalogs or invent grants. Current protocol interfaces remain backend-neutral.

### Storage and authority inventory

| Family | Canonical owner and representation | SQL treatment |
| --- | --- | --- |
| Canonical transcript, semantic, episodic, user and internal memory-plane records | Existing CanonicalMemoryRecord plus owning typed payload codec, original IDs/digests/visibility/source kind | `memory_batches`, `memory_record_versions`, `memory_current_records`, `memory_revision_state`; retain every batch and version, indexed latest pointers |
| Semantic entities, claims, relationships, evidence, temporal/trust overlays and event history | SemanticIngestionAtomicStore and registered semantic schemas; claims remain distinct from structural relationships | Derived typed `semantic_entities`, `semantic_claims`, `semantic_relationships`, `semantic_evidence_links`, `semantic_temporal_index`; original governed records/events remain canonical |
| Ontology proposals, evaluations, immutable versions, activation attempts, scope pointers and replay receipts | Existing learned/catalog owners, approval policy and source lineage | Typed indexes `ontology_versions`, `ontology_candidates`, `ontology_selections`, `ontology_activation_attempts`, `ontology_evaluations`, `ontology_replay_receipts`, backed by original canonical records |
| Execution, solver and runtime command state | RuntimeStateRepository and validators described below | Separate runtime tables and event profile; never reused as semantic fact tables |
| Packaged base catalogs and compiled bundles | Existing product-release verifier and immutable package resources | Verified bytes may be cached by digest; `catalog_resource_refs` binds exact package/version/member identities; SQL cannot issue release authority |
| Work-state, decision-state, trace/evaluation auxiliary stores and conflict/integrity files outside MemoryPlaneStore | Existing owners | Remain separately registered participants in this release; their migration is not implied by shared graph storage |

This migrates the entire memory-plane log, including its transcript and control records, rather than cherry-picking graph rows and breaking shared revisions. Logical memory domains remain distinct. Existing security/integrity authority that resides outside the memory plane stays with its owner and is enrolled in administration/backup. Ontology control records inside the memory plane are domain state, not the installation's independent root of trust.

No giant database blob replaces the old JSONL file. Immutable original batches and individual canonical record versions are retained for audit/replay; separately indexed rows support queries. Index rows carry canonical record ID/digest, source revision and decoder/schema identity. They are rebuildable and cannot be independently updated or treated as new facts. SQL foreign keys enforce structural closure within the partition; domain validators additionally enforce temporal, evidence, candidate/committed and cross-scope rules. A plain subject/predicate/object edge is insufficient to represent a governed claim.

Payload codec inventory is generated from the actual installed semantic event/content registries, semantic control classifier, learned-relation models and catalog authority models. It enumerates every supported source kind, namespace, schema version, owner, canonical decoder and index projector. Aliases, wildcard namespace handlers and unknown/future schemas are rejected. Existing legacy generic records may use an explicitly named historical codec and their original reader; they cannot be promoted into new semantic indexes or assigned a catalog from the current active pointer. Missing legacy decoder blocks that partition's migration with an itemized unsupported-format report. Migration cannot silently drop, normalize or reinterpret those records. The implementation ledger must enumerate concrete registry entries and cardinalities before code is added; generation parity covers every installed family.

### Transaction and compatibility contract

For the SQLite memory-plane view, preserve all existing protocol methods: durable flag, protected secret delegation, stage/upsert/write, governed policy installation, apply_batch, revision, detached get/list/snapshot, write/timed snapshot and linearized callback reads. `apply_batch` checks expected data revision, expected write revision, RecordAbsentPrecondition, RecordDigestPrecondition and RecordFencePrecondition with their existing meanings; the feature-owned opaque write authorization and transaction precondition still run inside the final authorization/commit fence. An absent expected revision remains the existing unconditional-write behavior, not a grant bypass. Wrong/stale preconditions preserve the original error class and make no partial batch visible.

Memory-plane write revision increments for each accepted batch; data revision increments only if the original visibility predicate `_contains_runtime_context` is true. Runtime-only commits do not change either memory-plane revision. Ontology internal-control batches keep their existing visibility-driven revision behavior; do not classify them by table name. Preserve batch order, original canonical digest algorithms, mutation fences, latest-by-ID semantics, first-insertion ordering of legacy list/snapshot results, detached copies and UTC timestamp/clock linearization. Generic record names or SQLite row IDs never become authority. The memory-plane unit of work keeps optimistic batch semantics; it must not hold a database write lock while a model runs.

One short partition SQL transaction publishes a domain batch, its history/current rows, derived indexes, domain receipts and its publication manifest together. Semantic group facts/events/dedupe/revision bindings stay in their existing atomic group. Ontology selection retains its prepared-attempt -> pointer CAS -> finalization/replay lifecycle; physical co-location does not collapse that lifecycle or make activation imply successful replay. Shared transactions are used for already-authorized mutations, never to let a runtime operation bypass the semantic writer. Cross-domain workflows retain durable outbox/receipt transitions; callers do not get a new arbitrary multi-domain transaction API.

Nested owner calls join only an explicitly supplied, coordinator-owned typed transaction context for the same partition and authority. They cannot open a second writer connection, commit a parent transaction, or perform external/model I/O. Calls without such context own a complete short transaction. Establish lock order installation barrier -> existing authority/integrity fences in a fixed documented participant order -> control publication lock -> partition SQL transaction; adapt existing callback/fence acquisition to this order before production enrollment. A linearized read retains the relevant grant/integrity fence through result release; a WAL snapshot alone is insufficient to preserve revocation semantics. Missing enrollment, recursive lock inversion or foreign transaction context rejects before mutation.

### Partition publication and indexed retrieval

The signed publication protocol below now covers the complete partition, not only runtime tables. Extend `RuntimePublicationState` with a closed `PartitionRevisionVector`: partition publication ordinal, runtime genesis-or-batch position, memory-plane write/data revisions, semantic genesis-or-batch position and ontology pointer-set digest. The publication ordinal is distinct from all domain event sequences. Every successful semantic, ontology or runtime batch advances it once; a domain without a change retains its head. The signed tuple binds the complete application-data manifest plus each domain's authenticated history/closure. A semantic-only commit cannot masquerade as a runtime event, and an ontology pointer digest is not an ontology grant. Checkpoints remain domain-specific and declare their vector; partition backup contains every domain checkpoint plus its required tail.

The manifest's closed SQL inventory includes all added canonical-version/latest-pointer/revision/index/catalog-ref tables. Original semantic batch checksums, event signatures and checkpoint verifier rules remain mandatory; the outer partition signature supplements them. No conversion to the runtime event profile or new hash algorithm is authorized for old semantic records. All prepared-intent recovery, genesis, verified-read, antirollback and quarantine rules apply to the full partition tuple. Genesis has empty domain histories/revisions and an empty pointer-set digest. Import creates a separately approved migration generation whose manifest binds the verified imported domain heads; it never fabricates genesis events for historical semantic data.

Add `MemoryPlaneQuery` and `MemoryPlanePage` as internal closed, typed reader contracts. Query variants are record lookup, filtered records, entity neighborhood, evidence links and catalog history; fields are finite domain/status/source-kind filters, authorized scope binding, bounded ID/time filters, page size and opaque cursor. No SQL text, caller-selected table or unbounded traversal. Default page size 100, maximum 500; neighborhood depth is 1 or 2 with explicit truncation. Page cursor binds query, principal/grant epoch, partition generation/publication ordinal and domain revision vector. Current read authority and forget policy are checked before returning rows, counts or cursors. SQL is a candidate-selection optimization; existing protected semantic/catalog readers decide eligibility and current/historical visibility. Unsupported query forms reject; an explicit existing full-snapshot compatibility method remains available to internal owners, not as a model escape hatch.

Indexes must support scope/domain/status/source-kind, canonical ID, entity/predicate endpoints, evidence references, validity intervals and catalog-owner/version lookup. An indexed query and the original authorized scan must return equal ordered results on the same snapshot, including exclusions. Verify reads using the full manifest or a verified immutable projection as below; SQL index corruption is not trusted because a query returned plausible rows. Changing backend alone is not a measured performance improvement. Capacity verification adds named growing semantic/ontology fixtures and compares write amplification, reopen time, indexed queries, snapshot verification and concurrent writer wait against JSONL. Required hot-path query plans must use the declared selective indexes; full-log rewrites per commit are forbidden.

### JSONL migration and cutover

`memorii migrate plan` detects an existing JSONL installation and produces a closed `MemoryPlaneMigrationPlan`: installation/partition identity, input root identity and byte digests, original write/data revisions and semantic heads, required schema/codec/catalog/key references, complete source/auxiliary participant inventory, target format/generation, required free space and preview digest. It is read-only. Managed SQLite startup on an unmigrated root returns migration_required as an unsupported-configuration detail; it never creates an empty database alongside old memory. New installations default to SQLite; JSONL remains a read-only import/export/diagnostic format after cutover, not a fallback writer.

Existing JSONL installations need a control bootstrap distinct from empty-root `init`. Owner-authorized `migrate apply` may perform `legacy_adoption` after locking/quiescing the exact approved legacy root and independently verifying its key/catalog/legacy-reader authorities. Create the new control database in a fresh owner-only sibling directory with the owner-pinned initial signer/registry. Its first atomic signed control transaction records `LegacyStorageSelector`: discriminator `legacy_jsonl`, installation/partition ID, exact root and file fingerprints, both memory-plane revisions, semantic heads, migration-plan digest and verified external authority references. InstallationControlState has a closed storage-lifecycle field `migration_only | operational`: adoption sets migration_only with operation mode read_only; verified cutover atomically sets operational and the owner-selected mode. Fresh empty initialization sets operational only after its genesis finalizes. Migration-only permits status, read-only diagnostics and authorized migration recovery; it denies ordinary data APIs, background work and normal backup. The initial control transaction also records the adoption receipt. This selector is an explicitly typed alternative to a SQLite publication tuple in a generation-change intent; it is not normal genesis, signed historical-event evidence or a grant inferred from legacy bytes. All ordinary data APIs remain unavailable until verified SQLite cutover.

Before this first control commit, a crash leaves legacy input intact and no published new authority. After it, only the same exact legacy selector and owner plan may resume migration; missing/mismatched input, ambiguous sibling state or unavailable independent authority quarantines. Duplicate adoption returns the same receipt and cannot reset the registry. The existing migration intent then transitions exactly `legacy_jsonl -> sqlite`: exact old recovery retains migration-only mode; exact new verified recovery finalizes active SQLite state; all third states quarantine. Atomic control initialization either exists in full or is unavailable, never partially trusted. Test fresh legacy adoption, every control/import/selector cut, duplicate/conflicting adoption, hostile precreated roots and missing key/codec/catalog authority. Normal `init` retains its empty-root restriction.

`migrate apply` requires owner authorization and an unchanged approved plan. Under the exclusive installation barrier, quiesce all registered writers including legacy host factories, reconcile pending publications and revalidate source identities/revisions. Hold write exclusion through import/cutover; fail visibly if quiescence or capacity cannot be established. Copy to a fresh generation; leave original JSONL and external artifacts untouched. Validate every original batch checksum, contiguous revision and registered record schema; store original batch bytes and all historical record versions, then rebuild latest pointers and typed indexes with original owners. Preserve IDs, timestamps, event positions, source/candidate lineage, grants, fences, pending attempts, catalog versions/pointers and protected legacy reader bindings. Invalid/truncated input, duplicate/conflicting bindings, unknown schema, missing evidence or unavailable checkpoint/key authority aborts before cutover.

Parity acceptance compares all historical batches and latest records, both revision counters, semantic genesis/checkpoint-tail reconstruction, graph/evidence/temporal results, ontology selected version/attempt state, protected allow/deny results and deterministic export. Import does not call a model, activate a catalog, retry an action or replay a source into new truth. Existing semantic protected secrets/checkpoint keys remain in their key owner; migration preserves their identity/purpose and verifies historical checkpoints, never generates replacement keys merely to make them pass. Immutable package catalogs retain original release fingerprints and member digests. External artifact closure is verified and registered for backup before publication.

After parity, publish the target through the existing owner-authorized generation-change intent, with source and target format tags, source fingerprints, validation-report digest and backend selector included in its signed pointer. Crash recovery accepts only exact old JSONL selector or exact new verified SQLite selector; all third states quarantine. Legacy composition roots must honor the same selector/barrier and reject post-cutover writes to old files. Copying files or changing a configuration string is not cutover. Idempotent repeat returns the completed migration receipt. Before any new SQLite-domain writes, rollback may select the unchanged verified old generation through an explicit owner plan. After new writes, refuse rollback to stale JSONL; use forward repair or a separately tested lossless reverse migration. A previous backup requires explicit acknowledged data-loss restoration and current security policy, never silent fallback.

### Alternatives and release sequencing

Keeping JSONL is already durable and minimizes change, but retains full-history replacement and a second storage lifecycle. Separate SQLite files per domain preserve owner boundaries but require coordinated multi-file backup/publication and cannot supply one physical transaction; SQLite WAL does not make attached database commits globally atomic. A shared application-data database with separate domain views is selected for local v1. Larger remote/multiwriter deployments may select another backend later; no distributed semantics are promised.

Implement shared infrastructure and SqliteMemoryPlaneStore parity first, semantic/ontology indexed readers and offline migration second, then runtime tables and harness recovery on the same partition coordinator; complete all-writer operations and Level 3 gates before release. Existing runtime design obligations remain. Old runtime-only approval is superseded for this expanded scope; no semantic/ontology SQLite backend or migration is claimed implemented.

## Durable Contract And Closed Grammar

All new external/persisted models are closed Pydantic schemas (`extra=forbid`), finite enums and explicit typed unions. Validate canonical values, sizes and references before transaction allocation. Reuse existing ExecutionNode/Edge, SolverNode/Edge and overlay enums but replace generic content dictionaries at this boundary with registered node-type content codecs. Existing unconstrained `EventRecord` is a legacy in-process model, not the new persistence format.

### Core records

Every record carries installation/repository identity, task scope, record ID, positive version, lifecycle and schema version. Solver IDs are bound to exactly one permitted execution node in the same task. The explicit schemas are:

- `TaskRecord`: task ID, principal/project scope, goal, creation time, root execution node, task lifecycle, retention tier, current active solver selection per execution node. The selection is explicit; lexicographically last ID is never current-state authority.
- `SolverRunRecord`: solver ID, parent execution node, existing solver category, lifecycle, creation source and selected overlay ID.
- Execution node/edge full snapshots with existing typed status, artifact/constraint links and acceptance criteria.
- Solver node/edge full snapshots with existing candidate state and provenance; node content is a closed discriminated union described below.
- `SolverJustificationRecord`: conclusion, supporting/contradicting/assumption IDs, finite numeric strength, active state, source refs and version. Overlay history explicitly references active/inactive justification IDs; no beliefs migrate onto structural nodes.
- `SolverOverlayVersion`: immutable full snapshot per version with parent overlay, ordered node overlays, frontier/reopenable/unexplained flags and justification refs. Exactly one committed selected overlay per solver revision; candidate overlays never replace it.
- Typed directory links for task graph, solver parent, host session binding, agent grants and writeback sources. Uniqueness includes principal/project/task; current bare IDs are not globally trusted.
- `ActionAttemptRecord`: host action ID, selected recommendation revision, executor binding, `selected | dispatched | succeeded | failed | outcome_unknown | cancelled`, evidence/result refs, delivery identity and version.
- `RuntimeCommandReceipt`: principal/client namespace, operation ID, canonical request digest, admitted mode/authority epoch, base/current revision, `pending | committed | rejected | needs_reconciliation`, bounded typed result/error and result digest.
- `SourceAdmissionReceipt`: original host source coordinate, content digest, typed role/modality, principal/scope, source owner/revision and eligibility. It references durably retained bytes; it does not convert model prose into user evidence.

Node content inventory: GOAL/QUESTION/ASSUMPTION/CONSTRAINT use typed text plus referenced evidence/validity; HYPOTHESIS/COMPOSITE_HYPOTHESIS/EXPLANATION_FACTOR/SYNTHESIS add constituent or conclusion references and explicit epistemic status; OBSERVATION uses source/result refs and observed summary; ACTION uses the existing typed action proposal plus source/evidence refs; SCENARIO uses typed conditions and expected observation refs; SEMANTIC_REF/EPISODIC_REF/USER_REF/ENVIRONMENT_REF/SKILL_REF carry typed domain/reference/revision/validity. No arbitrary nested extension dictionary is accepted. Each codec rejects unknown fields, wrong node kind, duplicate refs, nonfinite numbers, invalid timestamps and scope-incompatible references; content strings are data, never executable instructions. Model candidate reasons are short explicit records, not hidden reasoning traces.

TaskContext host metadata becomes a closed `HostBinding` (host kind/version, client installation, task, session, optional thread/branch, optional opaque bounded host cursor). Core never executes a cursor or imports a framework to interpret it. Task grants and host credentials are separate capability objects, never serialized into model context or backup manifests.

### Persisted operation and delivery state machines

`RuntimeOperationAttempt` is the recovery owner for a command receipt. Required immutable fields: receipt ID, attempt ordinal, request digest, source receipt/digest, base task revision, model binding/prompt/schema fingerprint or explicit no-model discriminator, and selected policy digest. Mutable fields are versioned full-state updates: stage, lease owner, strictly increasing fence token, UTC expiry, invocation count, token/cost allowance and amount spent, next retry time, staged candidate reference/digest, typed validation outcome, terminal error/result ref. No timestamp is used as a fencing token. One active attempt per receipt and one lease owner per attempt; unique `(receipt_id, attempt_ordinal)` and monotonically fenced takeover. Default maximum three model invocations; a configured lower budget wins. Unsupported model usage accounting disables automatic retries rather than guessing remaining budget.

| Owner | Allowed transition | Atomic conditions/effect |
| --- | --- | --- |
| command receipt | absent -> pending -> committed, rejected or needs_reconciliation | operation/digest uniqueness; terminal immutable; retry returns exact result, replan uses a new operation ID |
| operation attempt | prepared -> awaiting_model -> candidate_persisted -> validated -> committed | persist request before call; candidate closed schema/ref persisted under live lease; validation binds source/base/model fingerprints; final batch includes terminal receipt |
| operation attempt | awaiting_model -> prepared | lease expired and retry budget remains; increment attempt/fence before invocation; provider call may have occurred, so spend is conservatively reserved |
| operation attempt | candidate_persisted -> validated, rejected or needs_reconciliation | current authority/evidence and unchanged base; never request another model result merely because process restarted |
| operation attempt | any nonterminal -> rejected or needs_reconciliation | invalid evidence/grant, budget exhaustion, stale base or explicit cancellation; preserve staged bytes as protected candidate evidence |
| external action | selected -> dispatched -> succeeded or failed | unique dispatch reservation `(task_id, recommendation_id, recommendation_revision)` independent of caller action ID; current grant/mode/base; completion must match executor/result evidence |
| external action | dispatched -> outcome_unknown -> succeeded, failed or cancelled | host reconciliation only; cannot transition back to dispatched; intentional rerun requires a new authorized recommendation |
| external action | selected -> cancelled | no dispatch; a completed action cannot be cancelled retrospectively |
| outbox | pending -> delivering -> delivered, rejected or needs_reconciliation | stable delivery ID, canonical target request/source digest and target authority binding; current lease/fence/epoch; target receipt required for delivered |
| outbox | delivering -> pending | expired lease or retryable target outcome, bounded attempt/backoff; same target delivery ID; never reinterpret unknown target result as success |

`RuntimeOutboxDelivery` contains origin batch/command, closed kind `work_projection | writeback_candidate`, target protocol/owner, canonical typed payload ref/digest, required source scopes, delivery ID, version, status, lease/fence/expiry, attempt limit/count, next retry time and target result/ref. Work projection payload is a runtime revision plus typed WorkStateSummary; writeback payload is the existing typed WritebackCandidate. Target authentication is reissued by authority owner, never persisted as a bearer credential. Unknown targets reject before dispatch. Failed/revoked outbox delivery leaves graph commit intact and visibly pending/rejected.

The transaction protocol does not promise exactly-once model billing: crash after remote response but before durable candidate persistence can repeat the call. Persist before acknowledging candidate receipt; reuse provider idempotency where supported, otherwise consume the reserved attempt budget. Exactly-once applies to accepted logical graph effects. Dispatch reservation prevents two hosts from using different action IDs to execute the same recommendation; Memorii cannot prevent a host that ignores its dispatch protocol from executing a tool.

### Registered event profile

`RuntimeEventBatch` specializes the canonical event model: base envelope fields, canonical typed-value encoding, envelope/batch digest and repository batch sequence are mandatory. Reuse the existing canonical codec; do not invent a second digest format. Register the execution-runtime schema namespace without extending the semantic compiler's memory profile. Event type identifies schema, not a second event-ID alias. Every mutation contains full state; no ID-only commit event.

Legal combinations are closed:

| graph_type | entity_type | Operations | Entity union |
| --- | --- | --- | --- |
| execution | node, edge | create, update, delete | matching execution snapshot; delete is retained logical retirement |
| solver | node, edge | create, update, delete | matching solver snapshot; backtracking uses updates/overlays, not deletion |
| solver | overlay | version | immutable SolverOverlayVersion |
| system | directory | create, update, delete | TaskRecord, SolverRunRecord, typed directory link, justification, action attempt, command/source receipt, operation attempt; distinct discriminator required |
| system | checkpoint | create | RuntimeCheckpoint metadata/ref |
| system | routing | create, update | typed outbox delivery, policy/mode/forget record |

Each registered entity has a fixed graph/entity/operation set; no link/unlink alias, unknown discriminator, implicit inheritance or wildcard schema. All entity IDs equal record IDs in this profile; envelope IDs are separate. Event business labels (task started/resumed, solver started, action completed, etc.) remain explicit schema metadata mapped to existing EventType semantics. Schema generation must enumerate this mapping and its full-state type, including task creation, every overlay and directory change. Overlay version history is preserved. Unknown/unregistered types fail before exposure.

SQL tables retain typed canonical record bytes and schema identifiers, not executable pickle. Separate tables/indexes own task/execution/solver/overlay/justification/directory/commands/actions/outbox, complete event batches, event-ID binding, dedupe binding, record-version binding and checkpoints. All three event indexes and materializations publish in the same transaction. SQL uniqueness supplements domain checks; equal-version non-identical envelopes fail `memory_integrity_conflict` at append and replay, including older historical reservations. Current state alone cannot decide duplication.

## Transaction, Recovery And Source Flow

1. Trusted host maps user/session/project and authenticates a closed command. Core resolves finite read/write/action grants before lookup. Canonical request digest excludes server-assigned time/IDs, includes actual caller intent and source identity.
2. Under a short admission transaction, resolve duplicate command or allocate a pending receipt and record the receipt of already-completed idempotent source admission; no source-owner I/O occurs inside this transaction. Duplicate same digest returns prior status; divergent reuse fails without another source/event. Persisted intake can finish before reasoning and is explicitly not a committed graph result.
3. Release storage locks before model calls. Work uses one base revision, selected policy and durable source/evidence snapshot. Persist returned candidate output before retries can invoke the model again; a pre-response crash may repeat a model request, but cannot repeat committed graph effects. Bound worker lease, attempt count and remote budget; exhausted work gets a durable non-success terminal.
4. Validate staged full-state changes with existing candidate/commit validators, graph endpoint/acyclicity rules, overlay/justification closure and current evidence eligibility. Provisional model state cannot mark task done, strongly falsify committed state or request semantic truth directly.
5. Acquire the installation control fence then repository transaction (`BEGIN IMMEDIATE`). Recheck current grants, source eligibility, mode epoch, task base revision, lease fencing token and task completion evidence. Assign contiguous batch/record versions and atomically publish events, indexes, all changed views, result and outbox.
6. Complete the signed data/control publication protocol below before exposure or acknowledgement. Crash before commit exposes old state; crash after commit returns identical receipt on retry. On stale revision return `conflict` with a scoped current revision; never silently reapply an action proposal against different evidence. Reads use a single SQL snapshot with the same task/control epoch and revalidate release authority immediately before returning bytes.

Source admission and runtime acceptance remain distinct authorized operations even when they share the application-data database. Existing source owner durably admits raw evidence first via idempotent authenticated admission; runtime then records its exact receipt. Orphan retained sources are safe and visible as pending, never mistaken for semantic truth. Graph commit and a typed outbox record are atomic. Outbox invokes the existing canonical provider admission path with stable delivery ID; target's durable idempotency receipt handles crash-after-target-commit. Work-state summaries in the separately registered auxiliary store are projections of the runtime revision. Semantic/user writebacks remain candidates requiring their current independent governance; outbox dispatch does not bypass it. End-to-end status separates `graph_committed`, `projection_pending`, `writeback_candidate` and target outcome.

All source, grant and mode changes that affect eligibility participate in the installation barrier described below. Workers perform provider calls outside that barrier, then final eligibility validation inside it. Direct embedded writers must register or fail; otherwise backup/mode guarantees would be false. Existing semantic fence/checks remain in addition to this installation fence.

### Checkpoints and replay

Every accepted command is durable; checkpoints accelerate reads and never create durability by themselves. Default checkpoint cadence is 100 committed task commands, plus explicit pre-compaction/task-pause checkpoints. Make it configurable and validate bounds; failure leaves event history usable and reports degraded checkpoint health.

`RuntimeCheckpoint` includes task/context/directory, execution snapshots, all attached unresolved solver snapshots/candidates/justifications/overlay history or immutable verified refs, operation-attempt/action/outbox states, frontier/question/unexplained/reopenable indexes, all replay binding indexes, complete batch high-water position/digest, schema/reducer/planner fingerprints and authoritative selection pointers. Its canonical manifest includes repository/installation identity, all snapshot/index/member digests, schema registry and policy digests, creation control epoch, signing key ID/fingerprint and Ed25519 signature over a domain-separated canonical manifest digest (`memorii.runtime-checkpoint.v1`). The host injects an opaque `RuntimeCheckpointAuthority` signer/verifier; key bytes never enter the checkpoint or data generation. Reuse the existing checkpoint-authority protocol shape, not the semantic checkpoint key or purpose. The authoritative current key registry, allowed schema/policy history and minimum trusted sequence reside with the installation control owner.

Before any snapshot exposure validate signature, signer purpose/repository, current trust lifecycle, schema/policy history, member/index digests and complete batch position. Unknown/revoked signer, malformed/absent signature or unapproved policy rejects; a retired signing key verifies historical checkpoints only when current trust policy explicitly allows that key and sequence interval. Rotation retains public verification material and signed lifecycle history. A checkpoint with an older data/control epoch is usable only with an authenticated complete tail to the current committed watermark plus current grant/forget checks; never restore old policy authority from it. Invalid checkpoints are retained for diagnosis; genesis fallback needs independently authenticated complete event history.

### Closed publication and control authority

Fresh installation is an explicit owner-only `memorii init` operation, not an implicit side effect of `start_task`. The local owner is authenticated through OS ownership and the configured key owner; no model/host grant or test authority may bootstrap. Under an exclusive initialization lock, require absent or safely empty owner-controlled roots, reject symlinks/foreign or ambiguous precreated state, and provision installation identity, initial control format, approved schema/policy registry and signing identity through the key owner. Initial trust is pinned by that owner-managed identity, never by a key asserted inside the untrusted database. An interrupted key provisioning with no control state is reconciled by the key owner and cannot authorize data reads.

Publication position is a closed union `genesis | batch(sequence, digest)`: genesis uses a domain-separated fixed empty-chain commitment and no numeric event-batch position, so it does not invent a batch zero. The initial signed tuple binds an empty closed materialization manifest, no checkpoint, the new generation and initial trusted registry/eligibility epoch. The first atomic control transaction creates the initial registry/state, signed initial journal and a prepared publication intent whose expected-old discriminator is `uninitialized`; this variant is legal only for init on a verified empty root. Publish the empty data generation atomically, then finalize its tuple/control receipt using the normal protocol. On restart, prepared init plus verified absent data aborts safely and permits owner-authorized retry; prepared init plus exact signed empty generation finalizes; every other state quarantines. With no initialized control authority, the runtime factory rejects before any task call. Duplicate init on an intact initialized installation returns the existing initialization receipt only for the same owner/root/configuration; it never resets an installation. Conflicting duplicates reject. Test fresh install, every key/control/data/finalization crash cut, reopen, duplicates, and hostile precreated roots.

Tail batches are signed with purpose `memorii.runtime-event-batch.v1`, chaining the previous batch digest. A signed head alone does not authenticate SQL projections. `RuntimePublicationState` is the closed finalized tuple: installation/repository ID, data-generation ID, genesis-or-batch position, materialization-manifest digest, optional checkpoint reference/manifest digest, schema/key/policy-registry digests, eligibility epoch, and publication signature with purpose `memorii.runtime-publication.v1`. Checkpoint-only publication changes this tuple even without a new event head.

`RuntimeMaterializationManifest` enumerates every authoritative materialized catalog by closed catalog ID, row count and canonical digest of all typed rows ordered by primary key. Coverage includes tasks, execution/solver structures, runs, overlays, justifications, directory/source links, command receipts, operation/action attempts, outbox deliveries and all three replay-binding indexes. Derived frontier, paging and summary indexes must be covered or rebuilt solely from verified rows. No unlisted persisted index may influence results. To avoid self-reference, event batches, checkpoint bytes, publication manifests and signatures are excluded from this row root: the tuple separately binds the authenticated complete head chain and checkpoint manifest/member closure. Checkpoint members match verified state at their sequence; tail replay derives the current manifest. Missing or extra authoritative catalogs reject.

Before every released SQL snapshot, under the compatible installation fence, obtain a finalized control tuple with no pending intent and verify the snapshot's complete catalog manifest and authenticated checkpoint/head closure against it. Counts, paging, summaries and harness rendering use only verified snapshot rows. Alternatively serve a protected immutable in-process projection reconstructed entirely from verified checkpoint and signed tail matching that exact finalized tuple; never mix unverified SQL rows or reuse it for another tuple. Failures quarantine with `integrity_error` and no task-derived output. These checks cannot be skipped to meet performance targets.

The control owner uses an independent owner-only SQLite database with closed versioned records: `InstallationControlState` (installation ID, format, monotonic control revision, eligibility epoch, mode, participant registry and administration/forget/revocation references), per-repository `RuntimePublicationState`, `RuntimePublicationIntent`, `RuntimeTrustRegistry`, and append-only signed `InstallationControlJournal`. The trust registry enumerates public key IDs/fingerprints, purpose, repository, allowed sequence intervals, lifecycle and approved schema/policy history/minimum positions. Private keys remain with the opaque key owner. Journal entries bind prior digest, revision, exact typed before/after digests, operation kind and signer; record updates and journal entry commit atomically. Unknown records/formats/phases or invalid journal chains reject startup. Control revision changes on every durable control transition; eligibility epoch changes on mode/authority/policy changes. Historical tuples require current allowed trust intervals and current release eligibility.

`RuntimePublicationIntent` contains unique intent ID, repository ID, expected old and candidate new complete tuples, command/receipt or checkpoint-operation binding, authority epoch, monotonic fence token, and phase `prepared | finalized | aborted | quarantined`. One nonterminal intent per repository is allowed. Publication serializes with key/policy changes and administration. Under exclusive publication fence: validate/sign the complete candidate; persist prepared intent plus control journal; commit data rows, batches, indexes and manifest in one repository transaction; atomically finalize the new control tuple and intent plus journal; only then expose/acknowledge. No separate data-committed flag is trusted: verified data determines recovery.

Before startup reads, commands, backup or trust rotation, resolve a prepared intent: exact verified old tuple means abort and preserve old state; exact verified new tuple means finalize and recover the saved receipt; any third tuple, modified row with unchanged head, missing closure or corrupt control record quarantines. Without an intent only the finalized tuple is readable. Terminal intents remain journaled. Readers wait for resolution; lost acknowledgements return the original receipt only afterward. Aborting publication never acknowledges uncommitted graph results; admitted work remains retryable under attempt rules. This is a recoverable two-owner protocol, not a cross-file SQL transaction.

Control records never replay from runtime data checkpoints. Graph events may record non-authoritative mode/policy/forget projections for explanation; current authority always comes from the independent control owner. This separation applies to replay, migration and restore.

Threat boundary: authenticated digests/signatures plus current control state detect tampering or rollback of replaceable data files while the control/key owner remains trusted. Compromise or simultaneous rollback of that owner is not detectable solely from the same installation; quarantine/rekey/recovery requires owner-supplied current recovery material. Do not claim otherwise. Copying a database without its current control state is not a valid restore.

Replay verifies repository/schema/digests and full batches into isolated state, validates references against the completed candidate batch, and publishes only at batch boundaries. Existing durable rows are read-only projections during replay, not hidden sources of defaults. Checkpoint validity failure: use verified genesis history only if complete and current security policy permits; otherwise quarantine and report `integrity_error`. Never salvage a partial frontier. A retained tail alone cannot replace missing checkpoint/index history. After replay verify checkpoint indexes/frontier against the deterministic reducers. No network/model call is required for reconstruction.

## Resume And External Action Safety

`resume_task(task_id, host_binding, operation_id, expected_revision?, authority)` restores one consistent view and records one idempotent resume receipt. `get_state` is read-only. Missing authorized task is `not_found`; denied task does not reveal whether it exists. Resume does not change a running external action to success or run it again.

Compare time-dependent assumptions, environment references and artifact fingerprints against recorded validity. Expired or unavailable evidence produces `revalidation_required` and makes dependent recommendations non-actionable; source history remains unchanged. Host supplies fresh observations to clear it through normal validation. Reconstruct the saved frontier before any new planning; changed planner version is visible and must not silently replace saved state. Replanning is a separate recorded command.

Before executing a recommendation, host calls an authorized `record_action_dispatch` with recommendation revision and stable host action ID. Memorii validates it once and records dispatch. Host executes its own tool/approval path; it later submits a result with that action ID and durable native result evidence. On restart an unfinished dispatched action is `outcome_unknown`. Host reconciles by native idempotency/query capability or asks the user; automatic resend is forbidden without independently confirmed safe semantics. Duplicate results dedupe; conflicting results deny. Task-completed input is a claim: validate required acceptance/tests and unresolved blockers before marking DONE. A chat session ending is not task completion.

Hybrid mode is the initial contract: host owns planning, model invocation, scheduling and tools; Memorii owns durable memory, scoped state and evidence-backed recommendations. Existing `RuntimeTaskState`, `ResumeTaskResult`, `HarnessOutput`, provider state-summary and next-step surfaces evolve through versioned APIs; do not create a second planner facade.

Request strings never choose principal authority. Embedded mode receives opaque in-process capabilities from the same authority owner; Python objects cannot be serialized as proof. Remote binding is disabled. Existing `ScopedHostReadAuthority` remains memory-plane scoped; new runtime write authority is separate, with the same resolve/recheck pattern. ### Event-bus consumer mode

`RuntimeEventConsumer` is a packaged library plus `memorii consume` CLI. ## Operations And User Control

### One installation coordinator and fencing

`StorageAdministrationService` maintains typed `InstallationControlState` in its own durable control store, outside replaceable data generations. Its complete closed record inventory and publication/trust lifecycle are defined above; it also owns restore history and pending administration operations. It never embeds credentials in graph events. Every production composition root registers its actual writers: runtime SQLite, memory plane, work/decision/trace stores, outbox workers and host capture. Unknown/unregistered writers cause `unsupported_configuration` for active service and backups, not best-effort consistency claims.

Lock order: process-safe installation barrier -> authority/control lock -> one participant transaction/lock. No participant may acquire barrier after taking its own lock. Readers take compatible shared barrier; administration is exclusive. Workers never hold barrier during model/network calls. A single sidecar is default; embedded access uses the same process-safe barrier and current control state. Direct legacy writers are unavailable in managed production mode. Final commit and protected result release verify current epochs under barrier. Leases cannot override mode/forget/revocation. Maintenance failure never silently changes mode.

| Mode | Capture and writes | Reads | In-flight and restart |
| --- | --- | --- | --- |
| active | admitted under grants and capacity | authorized current views | commits require same current epoch |
| read_only | new capture, graph, projection and semantic writes rejected visibly | protected reads/export/status allowed | mode change waits for already-committing short transactions then fences workers; pending work stays durable; reads do not append audit to data owners |
| bypass | host stops calling data paths; accidental data calls unavailable | admin status only | no background drain; data untouched; explicit return to active required |

Mode changes/admin audit themselves are permitted control-store writes. `pause` CLI maps to read_only; `resume` maps to active after health/grant checks. Acknowledgement linearizes after epoch durability and participant quiescence. Read-only must not allow hidden expiry writes in existing protected-read owners: evaluate due expiration without serving expired content and defer durable bookkeeping. This requires explicit updates to their production roots; an unsupported participant blocks the mode transition. Host UI must display unavailable/paused memory, not success-shaped empty context.

Commands: `init`, `status`, `doctor`, `task inspect`, `solver inspect`, `explain`, `checkpoint`, `pause`, `resume`, `bypass`, `export`, `backup create`, `backup verify`, `restore plan`, `restore apply`, `retention plan`, `retention apply`, `forget plan`, `forget apply`, `partition erase`, `migrate plan`, `migrate apply`, and `consume`. Machine JSON and readable output have the same status. Destructive commands require owner-only admin capability, dry-run plan digest, current epoch and explicit confirmation; model tools cannot mint that confirmation.

Status includes mode, root/format/backend, task revision/checkpoint age, pending/failed work and queue age, capacity, last verified backup and grant/authority health. Avoid content and raw path/ID leakage in general metrics. `doctor` is read-only: validate formats/digests/references/permissions, checkpoint reachability, outbox state and current grants; never repair corruption by deleting rows. Quarantined data is exportable only through explicit authorized forensic mode, never ordinary recall.

### Backup and restore

Backup covers the installation's registered provider and runtime stores, raw source bytes, generated catalog/policy material needed for historical decoding and all data-owner outboxes/receipts. It excludes bearer credentials and private signing keys. Under exclusive barrier, freeze new writes, drain only already-committing transactions, record the revision vector/control epoch and create immutable participant snapshots using owner APIs (SQLite online backup, locked canonical JSONL snapshots). Copying live WAL/main files separately is forbidden. Release barrier after immutable snapshots exist; pending work is included, not silently drained. Include each participant ID/schema/high-water/digest, source-closure manifest, format fingerprints and creation mode in `InstallationBackupManifest`.

Encrypt archive content using existing cryptography library AEAD with fresh per-backup content key, authenticated manifest and unique per-chunk nonces; wrap the content key with an operator-provided local recovery key. Do not put the recovery key in the archive or command logs. Validate encryption tamper/finalization, unpack limits and path traversal. Interrupted backup has no complete marker and is unusable. Default last-known recovery point is the last verified backup; status reports its actual age, not a promised zero-loss RPO.

Restore is offline into a new staging generation. Verify archive, participant inventory, schema versions, complete replay/reference closure and installation identity. Reapply the current control owner's revocation/forget journal before any reads; mint fresh host credentials and grants rather than restoring authorization handles. A fresh host must receive the latest independent control journal/recovery material from the owner; if freshness cannot be established, restore stays quarantined. Never trust an old data backup as current revocation authority.

The exclusive barrier publishes one fsynced generation pointer only after every participant validates. Recovery observes old generation or new complete generation; in-progress restore never overlays active directories. Mode remains read_only for smoke verification; explicit activation follows. Before rollback, account for post-backup accepted commands and outbox effects; require a plan showing potential loss and owner decision. Backup restore cannot retract external actions; unresolved action attempts remain reconcile_required.

### Independent control recovery and migration

An ordinary data backup binds its observed control revision/journal digest, finalized tuples and trust-registry digest; it never overwrites current authority. Before snapshots, resolve every prepared publication intent or fail backup. `backup create` also emits a separately encrypted, signed `InstallationControlRecoveryBundle`: complete typed control snapshot, validated journal through its revision, public trust history, participant registry, current forget/revocation state and finalized tuples. Prepared intents, private keys and bearer credentials are excluded. The owner retains a separate `InstallationRecoveryAnchor` (installation identity, trusted signer fingerprint, control revision and bundle digest) in an independent trusted recovery channel. Signing-key recovery or rotation is a separate key-owner procedure.

Fresh-host restore requires the owner's current bundle and independently supplied matching anchor, validating signature, full journal and format before control creation. Missing or mismatched inputs quarantine. Existing control state must agree with or extend the bundle; stale bundles cannot replace it. Supplying an old valid bundle and old matching anchor is simultaneous control-authority rollback and remains the stated threat limitation, not detectable freshness. A data backup alone cannot recreate security authority.

An older data backup cannot satisfy the current watermark automatically. Owner-approved `restore apply` resolves intents, verifies backed-up history/closure and current forget/revocation policy, then records `InstallationGenerationChangeIntent`: operation `restore | migrate`, exact old/new generation/publication tuples, control revision, preview digest, explicit data-loss acknowledgment where applicable, and phase `prepared | finalized | aborted | quarantined`. Under exclusive barrier, stage/verify candidate, durably prepare intent, atomically switch data-generation pointer, then finalize control tuple and journal. Recovery accepts only exact old or new pointer plus verified tuples; other states quarantine. Only this authorized administration transition can select an older data head; ordinary publication cannot decrease it. Security epoch and control journal never roll back. Current publication signatures bind restored history without rewriting historical events.

Control-format migration separately copies and validates the control database and full journal, requires no unresolved intent, and uses an owner-authorized atomic control-generation pointer switch recording old/new format and digest. Unknown formats reject before writes; pre-switch failure retains old generation. Once new control writes exist, downgrade is read_only unless a tested reverse-compatible reader preserves the complete journal and monotonic revision; never restore an old control backup to start an old binary. Test every pointer/intent/finalization crash cut. Backup, restore and migration share the exclusive barrier and cannot overlap key rotation or publication.

### Forgetting, erasure and retention

Separate four operations: correcting a fact (existing semantic lifecycle), logical forgetting (release suppression), archiving (tier/access policy) and physical erasure (explicit owner destruction). Do not present any one as another.

`forget plan` resolves exact authorized source/record scope and derives dependency closure through provenance, solver justifications, projections, caches, writebacks and retained replay. `forget apply` durably writes content-free suppression identifiers and increments control epoch under the barrier before acknowledging; invalidate cached/paged views and fence work using affected sources. Suppressed source evidence is ineligible for replay/promotion, its dependent conclusions cannot be served as evidence, and solver recommendations become revalidation_required. Do not disclose a redacted record's title/count/summary through another path. Recompute mixed-source conclusions only by a new normal validated operation, not by simply dropping a citation. Ordinary user export respects suppression; owner forensic archive access is distinct and explicit.

Logical forgetting retains historical backup/audit bytes and MUST say so; backups are encrypted, active SQLite/JSONL relies on owner-only permissions and documented encrypted-volume deployment when confidentiality at rest is required. First-release physical erasure is whole authorized, physically isolated storage partition only, not arbitrary event surgery. Plan enumerates all registered copies, descendants, caches, backups and shared references. If a file or backup mixes partitions, v1 rejects partition erasure as `unsupported_configuration`; the owner may explicitly erase the whole installation instead, after a separate complete preview. Do not rewrite signed semantic history to salvage unrelated rows. Erasure destroys the isolated partition and controlled backup copies/keys, invalidates replay eligibility and retains only a content-free erasure receipt in independent control state. If an offline/external backup copy is unaccounted for, result is `erasure_incomplete`, never `erased`. No secure-media overwrite guarantee is claimed. Selective physical record erasure is unsupported in v1; offer logical forget or full isolated-partition erasure with clear preview. This is explicit user-requested data destruction, never graph revision/backtracking. Normal event replay never deletes history. Suppression identifiers use opaque record coordinates/installation-keyed tags, never source text or raw native user identifiers.

Retention tiers HOT/WARM/COLD/ARCHIVED change availability/indexing, not semantic truth. Default automatic destructive pruning is off. Age alone never removes unresolved tasks, candidates, active evidence, event indexes, replay tails or action/outbox receipts. `retention plan/apply` may move completed partitions to verified archive and compact replaceable indexes/checkpoints while preserving canonical event history and restore ability. Expiry of evidence is a validity condition, not deletion. Physical removal uses the separate erasure protocol. Failed archive verification leaves original intact.

### Capacity and service envelope

Configured default admission bounds: command body 1 MiB, one staged batch 10 MiB, 1,000 pending commands per installation, 100 per task; cap graph context independently as above. Reject over-limit before source/model work, return `resource_exhausted` with safe limit name and retryability. Runtime repository enforces configured disk budget plus a reserved control/recovery margin (default 256 MiB); root free-space preflight and commit failure both matter. ENOSPC/IO errors roll back, mark explicit unavailable/degraded health and never acknowledge data commit. Recovery never spends unbounded model calls.

Before release publish measured supported task/graph/source sizes, p50/p95/p99 state-read/capture/commit latency, reopen/replay time, checkpoint/backup pause and bytes per command on named Linux/macOS fixtures. Operational targets for the initial reference fixture (10,000 execution nodes, 50,000 solver nodes across tasks, 100,000 events, 1 GiB provider sources): no-model bounded state read p95 <= 250 ms warm; durable no-model command p95 <= 500 ms; validated checkpoint resume <= 5 s; exclusive backup snapshot pause <= 5 s. These are proposed acceptance budgets, not measured promises; failure requires optimization or an explicitly revised supported envelope before release, never post-hoc claiming success. Model/host latency is reported separately. This is engineering capacity verification, not the deferred agent-benefit benchmark plan.

## Compatibility, Rollout And Alternatives

No existing durable execution format exists to migrate automatically. Existing live in-memory state can be exported by an explicit full validated importer with provenance marked imported; incomplete legacy ID-only event logs are rejected as restoration sources. Existing provider JSONL bytes/IDs retain their historical owner/reader semantics through the shared-storage migration specified above. New graph store must not reinterpret a work-state summary as a full execution graph.

Version generated wire/schema manifests and repository format; unknown future versions fail before writes. New event schema migration uses pure deterministic upcasters after validating original bytes, preserving original events/digests and explicit migrated views. Migration writes a separate generation; verify genesis/checkpoint-tail equality, counts, IDs, bindings and supported historical reads before pointer switch. Old binary refuses new writable format. Rollback after new-format writes requires a tested reverse-compatible reader or remains read_only with forward repair; restoring a pre-upgrade backup requires explicit loss reconciliation.

Roll out in order: shared partition and memory-plane parity/migration; durable public runtime and process proof; hybrid host state journey; complete operator controls and all-writer enrollment; second/third real host conformance; full Level 3 packaging/migration/authority gates. Until all-writer enrollment is complete, do not expose backup/mode/forget as supported installation operations. No provisional demo can be labeled production persistent mode.
