# Installed Structured Facts And Pre-Catalog Reads

Status: The first installed no-key Hermes journey, projection-era pre-catalog reader, and captured-turn catalog pin for versioned ontology selection are reviewed Level-2 contracts. This document adds those three narrow contracts to [the learned ontology design](learned_ontology.md). It does not change the ontology grammar, base catalog, learner, or single-account household scope. The governing Memorii architecture and authorization contracts retain their precedence.

## User journey and authority

A signed-in user gives Hermes a factual statement. The first-party host retains the exact user message under its verified installation, session, principal, and agent identity. Hermes may call a `memorii_submit_fact` provider tool with one closed `ProviderSemanticProposal` and exact quotations from that message. The tool cannot supply source bytes, source IDs, grants, principal, agent, catalog owner, catalog digest, operation ID, or a model credential. The host resolves the current retained message and creates the existing core `StructuredFactSubmissionRequest`; core validates it through the no-key structured path. The tool returns only the closed status and, when allowed, a core-derived operation ID. A later scoped read can return the committed fact using current fact and catalog-visibility grants. No OpenAI key or network call is needed for this sequence. Without an explicit structured proposal, raw-text extraction remains visibly pending when no authorized model is configured.

The tool is a first-party Hermes adapter convenience, not an ontology owner. Other agents can use the same generic core port with their own authenticated source and authority resolvers. Provider-generated prose is untrusted. Even when the provider tool is enabled, a model cannot turn its own text into authenticated user evidence or issue a grant.

## Hermes callback and tool contract

The first-party factory may advertise `memorii_submit_fact` only when its verified local installation authority, authenticated ingress, source-retention path, structured submission resolver, and protected read authority are all available. The OpenAI-compatible function schema has one closed arguments object: `schema_version: 1`; `proposal`, the fact-only subset of `ProviderSemanticProposal` defined below; `source_quote`, `subject_quote`, `predicate_anchor_quote`, and `object_quote` as nonempty strings; and an optional `source_quote_start` integer. No additional fields are accepted. The tool result is a JSON object with `status` in `committed|abstained|rejected|unavailable|denied|authorization_revoked_before_commit`; `operation_id` appears only under the existing core response rules. It contains no retained source, private grant, catalog internals, or fact payload. Malformed tool JSON returns a closed `rejected` result without a write. A missing or expired host turn context returns `unavailable`, not a guessed source. The provider must not advertise a tool that always returns unavailable.

`on_turn_start` is the synchronous host capture boundary for the current user message. The bridge verifies the callback author against the factory-pinned signed-in account and obtains the pinned agent and session. A new captured-turn admission owner prepares the canonical governed user source and the deterministic `PreparedSource` under the verified active bootstrap profile before publication. It publishes the source, admission index, prepared-source artifact and an idempotent capture ledger in one CAS using an extension of the source-only publication contract. The prepared artifact contains the exact retained sentence/token spans accepted by `ProviderMemoryService._validate_structured_source_spans`; no model transport runs during preparation. It creates no pending preplanning operation or selected semantic pipeline and must not call the activated `admit_source` path. The turn coordinate is a domain-separated digest of installation, session, authenticated user and agent, host turn ordinal, and exact message digest; callback clock is not identity. Repeated delivery of the same coordinate and bytes returns the same retained source. The same coordinate with different bytes, changed author/agent/session, or ambiguous concurrent turn context is denied. Only after that atomic source-plus-preparation publication succeeds and an exact read-back verifies its profile, source digest and spans may the bridge publish a provider-instance active-turn handle containing the retained source coordinate and an opaque generation. Because Hermes tool dispatch supplies only tool arguments, the handler resolves this host-owned handle under a lock rather than relying on a context variable crossing callback execution. Parallel tool calls within that one active turn may share the handle; a second overlapping turn on the same provider instance makes both ambiguous and denies submission until the host resolves the overlap. Tool arguments cannot supply the coordinate or generation. The handle enters a closing state before completed-turn handoff; the bridge waits for in-flight tool submissions before the completion CAS, and later tool calls are unavailable. It also expires at a bounded lease and cannot be used by another turn or process. A crash before the CAS leaves no capture or tool handle; a crash after it recovers the same complete source, prepared spans and ledger on exact retry. A missing or corrupt prepared artifact makes the tool unavailable and cannot be rebuilt under a changed profile. Restart may verify the durable capture ledger but cannot silently restore a live tool context.

Turn-start retention is inert: it records authentic raw evidence and a pending observation, with no model call, fact assertion, candidate, or graph mutation. A new `complete_captured_turn` transition verifies final user content, authenticated identity, session, and ordinal against the durable capture ledger. In one CAS it admits only the assistant source and marks the capture completed. If no retained structured submission exists for the captured user source, it also creates a semantic pending operation referring to that source through a distinct core-derived operation fence and returns it to the existing worker. If a structured submission exists in any pending or terminal state, it creates and enqueues no ordinary semantic operation; structured recovery alone owns that proposal, and the assistant evidence remains separately retained. The completed-turn callback does not retry extraction after a structured abstention or rejection. It does not call the two-source composite admission path, whose transcript-derived user identity differs from the captured identity. An exact completion retry recovers the same transition and operation; a changed completion is denied. If no turn-start capture occurred, the existing completed-turn admission remains available. The joined callbacks identify one original user-message lineage for recurrence and replay; completion cannot create a second independent observation. A crash after retention but before completion leaves inert evidence and pending status, not retryable graph work. A crash after completion recovers at most one owning pending operation: the structured operation when it exists, otherwise the ordinary completed-turn operation. A structured terminal uses its existing identity and retry path; the completed-turn worker cannot overwrite, reinterpret, or double-commit it.

### Captured-turn completion storage

The source-only capture CAS also creates one typed `HermesCapturedTurnCoordination` control at `semantic_ingestion:hermes_capture_coordination:` plus the SHA-256 of `b"memorii.hermes.capture-coordination.v1\0"` followed by the UTF-8 retained user `source_id`. Its closed schema version is 1. Immutable fields are `capture_id`, `source_id`, `source_digest`, `installation_id`, `session_id`, `principal_id`, `agent_id`, `turn_ordinal`, and `message_digest`, copied from the exact capture ledger and admitted user source. The mutable `state` is exactly `captured`, `structured_pending`, `completed_structured`, or `completed_ordinary`. `first_structured_operation_fence_id` is absent in `captured`, set on the first transition to `structured_pending`, and never changed thereafter. `completion_digest`, `assistant_source_id`, and `assistant_source_digest` are absent before completion and immutable thereafter. `ordinary_operation_fence_id` is present only in `completed_ordinary`. The record is internal control evidence; its timestamp is not an identity or retry discriminator. Unknown or partial fields, invalid state transitions, changed immutable fields, and a coordinate that does not join exactly one retained capture ledger fail closed.

### Catalog pin before tool-schema egress

The representative packaged `reports_to` child belongs to the shared `base` catalog, which the governing ontology design reserves to **product release authority**. It is not a learned candidate and the signed-in user's Hermes local-tool artifact does not authorize catalog activation. For this bundled base update, a first-party package-release manifest carries a closed `PackagedBaseCatalogReleaseDecision`: schema version, `CatalogAuthorityScope(base)`, product release identity, verified package fingerprint, parent seed version digest, child declaration digest, exact child version and runtime-bundle digests, `select_on_install` policy, and a domain-separated decision digest. The core package verifier accepts it only when the manifest's canonical byte digest equals the release root digest compiled into the installed Memorii package for that product release, and every referenced package index and descendant byte passes its pinned digest and typed validation. Only the product release build may change that compiled root; a loose JSON file, model output, sidecar or agent setting cannot issue it. A Level-2 local trial may substitute a test-only verified package/release-root fixture through the existing explicit scenario-test host, never through the production constructor. Authenticated release signing and multi-platform package provenance remain Level-3 rollout evidence. A future learned candidate uses the separate scope-owner `activate_candidate` protocol, never this packaged-base release path.

The release byte derivation has no self-reference. First compile the semantic child declaration and actual descendant members, then hash them into the runtime-bundle manifest. Next derive the schema-2 child version from that bundle digest, then write the package index mapping the finished version digest to the bundle digest. The **package content fingerprint** is the domain-separated digest of a sorted closed inventory of `(relative resource path, SHA-256 canonical member bytes)` for the seed compatibility resources, child declaration, child version, package index, bundle manifest and every referenced descendant. It excludes the release decision/manifest and the source module or carrier containing the compiled release-root digest. The decision binds this finished content fingerprint and version/bundle identities; its canonical bytes and decision digest are then placed in the release manifest. Last, the product release build compiles the digest of those exact canonical release-manifest bytes into the release-root carrier. The verifier repeats that order, checks the exact inventory cardinality and paths, compares every member hash, recomputes the content fingerprint and decision digest, and finally compares the release-manifest digest with the independent compiled root. No stage hashes bytes that contain its own digest, and a package index or descendant change cannot be accepted by editing only the decision file.

`CatalogReleaseInstaller.apply_packaged_base_release` is a core action invoked by each verified host composition after its semantic writer admission is established and before that host advertises a semantic schema; the Hermes factory is one concrete installed caller, not the catalog owner. The core release installer and package authority are framework neutral, so a different host uses the same action rather than inheriting Hermes configuration. On a fresh store, the host first calls the core `SelectedCatalogAuthorityRepository.ensure_seed_genesis`: it verifies the exact complete seed version/pointer pair or atomically creates the already restricted two-record genesis closure, and it denies partial, substituted or mismatched state. Concurrent initializers accept only that exact winning pair. Only after the verified parent exists may `apply_packaged_base_release` evaluate the packaged decision and its parent/pointer preconditions. With no valid release decision it leaves the existing selected seed untouched and reports child unavailability rather than selecting package bytes. If a verified installed release decision requires `select_on_install` but its exact publication/selection is not durably complete, the pin owner advertises no semantic schema and never falls back to the seed merely because the old pointer remains selected. With an exact valid decision, the release owner writes the decision and immutable schema-2 child `CatalogVersion` in one writer-governed CAS. The writer policy accepts only that two-record closed release closure after rechecking the package authority, parent/scope/declaration/bundle/version digests, current writer and parent version, and record absence; it preconditions the existing parent/pointer and product-release-authority identity. This is publication, not selection. A second catalog-owner CAS writes a new versioned selection attempt and pointer naming the decision digest and child version, with preconditions on the published decision/version, current release authority, writer, and expected prior pointer digest. A crash before this CAS leaves the old pointer active; an exact retry resumes the same decision/version and either completes that selection or observes its exact selected attempt. A changed release, stale pointer, partial publication, missing capability or different scope denies without silently choosing a newer package. No product file installation by itself mutates the pointer; the explicit core release action is the activation trigger. A later full 53-relation default release must use its own verified product release decision and complete bundle before selection, rather than claiming this four-relation checkpoint ships the base.

The capture CAS above retains the authenticated source even when no semantic catalog can be selected. A captured turn has no provider-facing semantic tool until core persists a catalog pin for that exact capture. The pin is created on the first eligible `get_tool_schemas` call, after the source, preparation, ledger and coordination have been durably verified and **before** a schema containing that catalog's predicates is returned. A failed catalog lookup, unavailable capability, denied current tool authority or failed pin CAS leaves the source intact and returns no tool schema; it does not start a model call, allocate a retained structured operation, or silently use the packaged seed. A later schema call may retry only while the same live captured-turn handle is open and unambiguous. The core pin owner, not the Hermes adapter, selects the catalog for the authenticated `CatalogAuthorityScope`; the factory supplies an expected digest only as a consistency assertion.

`CatalogCapturedTurnPin` is an immutable, closed schema-1 internal-control record in the execution domain. Its ID is `semantic_ingestion:catalog_capture_pin:` plus SHA-256 of `b"memorii.catalog.capture-pin.v1\0"` followed by the UTF-8 `HermesCapturedTurnLedger.capture_id`. Its fields are `schema_version`, `capture_id`, `source_id`, `source_digest`, `catalog_scope`, `selected_version_id`, `selected_version_digest`, `catalog_digest`, `runtime_bundle_digest`, `selection_pointer_digest`, and `pin_digest`. `pin_digest` is the repository's domain-separated typed digest of all prior fields under `memorii.catalog.capture-pin.v1`; neither timestamp nor WorkPlan/requirement identity enters it. The runtime bundle digest names the verified package capability closure for the selected version: the old fixed profile's verified manifest for the seed, or the complete generated writer/reader/prompt/schema/policy/adapter/tool manifest for a child. A child with an incomplete or stale capability closure is unselectable. The pin stores a selection witness, not a mutable declaration body or a fact-scope grant. Its owner/scope does not widen the authenticated source or fact scope.

The runtime bundle has one immutable **package-member authority** for this first bundled child. A package index keyed by `(catalog_scope, selected_version_digest)` gives exactly one content-addressed bundle-manifest member; the index itself is covered by the installed package fingerprint. The manifest's closed schema contains the scope, **parent version digest, semantic catalog digest and catalog declaration digest**, every required capability ID, each relative package-member path and SHA-256 of that member's canonical bytes, and its own typed content digest. It does not contain the child version digest: the version digest includes the bundle digest, so including the version digest in the bundle would make a circular hash. The verified index entry binds the finished version digest to that bundle digest. Paths are fixed package-relative resource identifiers without traversal, aliases or network fetches; duplicate keys, duplicate capability IDs, missing members, extra members, inconsistent digests and unknown artifact kinds deny. The verifier loads the manifest and **actual** prompt, output schema, Hermes grammar, adapter, state, temporal, trust and protected-reader members, hashes each byte sequence, validates its typed contract and shared catalog digest, and returns one immutable verified bundle object. The `runtime_bundle_digest` is the manifest's digest only after these checks; declared digest strings alone are not capability availability. The selected child `CatalogVersion` uses a new closed persisted schema that includes this bundle digest and parent/version identity in its own content digest. The core packaged-base release owner writes that immutable child version only with the verified product release decision above: the writer policy parses schema 2, verifies its parent/scope/content digest and exact package-indexed bundle bytes, and rejects overwrite or a version without every required capability. The release action then selects it through the separate authorized pointer CAS; neither a package file alone nor a model output changes selection. The pin CAS later preconditions that selected version record's digest. The existing seed version remains at its original schema and digest; a separately pinned immutable seed-to-old-profile package-index entry binds that exact seed version digest to the verified legacy profile manifest and source fingerprints. The seed is never mapped by today's active pointer or sidecar. All package revisions supporting historical child or seed facts must retain their exact bundle members; absent or changed historical bytes make schema, submission or affected protected read unavailable rather than loading current artifacts. Later dynamically learned catalogs require a separately specified immutable bundle-persistence owner before they can be selected; this bundled-child locator cannot be treated as general learner publication.

The canonical core catalog-pin owner reads one memory-plane snapshot containing the exact capture ledger, admitted source, prepared source, coordination, selected pointer, immutable selected version and the three current structured-grant states. It independently loads the version's package-indexed runtime bundle and verifies its actual bytes. It joins the ledger's principal, agent, installation, session, source digest and preparation fingerprint to the live authenticated capture and checks the current local structured-tool artifact. For an absent pin it uses one writer-governed `conditionally_write_records` transaction containing only the new pin record. Preconditions require pin absence and the exact current record digests of capture ledger, admitted source, prepared source, coordination, selected pointer, selected version, **each of the source/fact/catalog grant states**, and semantic writer admission; the writer policy validates the same closed pin grammar, source/scope/grant joins and selected version/bundle digest against the transaction's current records and verified package bundle. The verified factory/runtime may request this owner action, but neither tool arguments nor adapter code may write the pin or choose its contents. The existing catalog-genesis administration grant does not authorize pin writes. A pointer change, grant revoke or coordination completion before the CAS makes it lose and re-evaluate only while the live capture remains eligible. A capture succeeded before a catalog became available is therefore a valid retained-source state, not a partial semantic transaction.

The local structured-tool authorization is a verified file artifact, not a memory-plane record; its digest cannot honestly be a memory-plane CAS precondition. The factory validates it immediately before the core pin request and again after the pin CAS and before schema egress. A changed, expired or revoked file between those checks may leave an inert pin record, but **no schema is returned and no fact is authorized**; every tool call and protected read revalidates that file and the current same-store grants. The pin never serves as a reusable authorization token. Same-store grant revocation is serialized against pin creation by the exact grant-record preconditions above and against fact commit by the existing terminal fence. Refreshing the file does not reactivate a revoked same-store grant or restore a closed turn. These are the distinct guarantees for file-backed host authorization and transactional grant state; the design does not claim one atomic transaction across both stores.

If the pin already exists, core validates every typed field, digest, ledger/source/coordination join, immutable selected version and historical runtime bundle, and returns that exact pin without consulting the **current** pointer for selection. A present malformed, substituted, missing-version or retired-capability pin is unavailable with no fallback or replacement. Two concurrent schema calls may race to insert: one wins; the loser reloads and accepts only the exact verified winner for the same captured turn. If the active pointer rotates after the winning CAS, repeated schema calls and tool submission retain the pin's prior owner/version/digest. If it rotates before the CAS, the precondition fails and a retry may select the newly verified active version; no earlier schema was exposed. A crash after the pin CAS leaves a complete retained pin but no restored live tool handle. A restarted process may verify it for exact capture recovery/status and later operation retry; it cannot advertise the former turn's schema or accept a tool call until a new authenticated live turn is captured. Catalog selection failure never erases the retained user source.

`HermesCompletedTurnRuntime.get_tool_schemas` rechecks the same active-handle generation, expiry, closing state and current tool authorization after core pinning and immediately before returning a schema generated from the pin's verified runtime bundle. A changed or ambiguous handle yields no schema even if a pin was just persisted. `handle_tool_call` loads the persisted pin through core and verifies its capture/source join and schema-capability identity; the in-memory handle is only a locator. The factory's captured-tool resolver is a distinct closed authority variant: given the host-owned `capture_id` and exact pin ID/digest, it resolves the historical selected version and package-indexed bundle and returns the pinned catalog owner/version/catalog/bundle coordinate with current source, fact and catalog grants. It **does not** invoke the old three-predicate seed resolver for a captured child. A missing pin or any changed host identity, source, scope, bundle, grant, or proposal predicate denies before retained-operation allocation. The generic noncaptured resolver keeps its independent core-selected catalog path and never fabricates a Hermes capture ID.

`StructuredFactSubmissionRequest` carries a typed captured-pin reference only for a source proved to have a `HermesCapturedTurnLedger`; the reference includes `capture_id`, pin record ID and `pin_digest`. `ProviderMemoryService.submit_structured_fact` recognizes that source identity under authenticated ingress, reloads and validates the pin/version/bundle through core, compares it with the resolver's complete selected coordinate, and **does not reselect the active pointer**. It uses the pinned bundle's prompt/schema, adapter, state, temporal and trust authorities for this operation. The canonical immutable proposal envelope and retained `RetainedStructuredSubmission` payload include the capture/pin IDs and digests, selected owner/version/catalog/bundle digests and proposal bytes/digest; the core-derived retained operation ID is allocated only from this complete envelope after tool arguments exist. The captured publication CAS binds the same tuple to the operation link, control and coordination transition; an exact retry loads and compares all of it, while reuse of the operation ID with a different pin or payload denies. The pin cannot replace the later proposal-containing operation or authorize a commit by itself.

The new structured claim catalog binding has a closed schema version with claim ID, fact scope, catalog owner scope, selected version ID/digest, catalog digest, runtime bundle digest, and capture-pin digest for captured submissions (absent for generic noncaptured submissions). The final fact/event/binding CAS under the existing current-grant commit fence verifies the persisted pin, pinned bundle capability and exact selected tuple; it never asks the current pointer to reinterpret the fact. Protected read uses the fact's stored historical selected version and actual verified bundle bytes plus current fact/catalog visibility grants. Existing schema-1 seed-bound claims continue through their existing verified seed compatibility reader, while truly unbound pre-catalog projections continue through the separate projection-era legacy reader; neither is assigned a child version. Missing or corrupt historical bundle, binding or pin makes the affected release unavailable with zero items/counts/snippets, including after rollback. A proposal unsupported by the pin's version, wrong bundle, revoked grant or changed capture context gives a noncommitting denial/unavailable result with zero new fact, event or binding and no alternate current-catalog retry.

The installed deterministic matrix includes: source capture succeeds with no selectable catalog but exposes no tool; first schema call persists the pin before egress with no OpenAI key or socket access; exact and simultaneous schema retries return one pin; pointer rotation before the pin CAS selects only the winning current version, while rotation after it leaves schema, proposal and commit on the stored version; JSONL reopen verifies the pin but restores no live handle; missing, corrupt, substituted or partial pin/version/bundle denies schema, submission and protected result; closing or expired capture denies; same-store source/fact/catalog grant revocation between pin validation and its CAS leaves no pin, and revocation before commit yields no committed fact/event/binding. File-backed local-tool authorization replacement between pin CAS and schema egress may leave only an inert pin: no schema or submission succeeds. The installed `get_tool_schemas` -> `handle_tool_call` -> canonical terminal -> protected read path must prove one new relation and a pre-upgrade old fact under separate historical readers.

The installed root also proves caller omission and stale descendants rather than relying on a helper test. With the core pin owner removed from an otherwise verified factory/bridge, `on_turn_start` still retains the user source but `get_tool_schemas` returns `[]`, with no pin, operation, fact, event, egress or seed fallback; restoring the owner restores the exact pinned child schema. For a selected child, independently stale one generated prompt/schema, adapter, state/temporal/trust, tool-grammar or reader member while leaving the pointer valid; the package verifier denies the pin/schema with zero effects. After a previously valid pin, remove or substitute a historical bundle member and reopen JSONL: tool submission and affected protected read return unavailable with zero items/counts/snippets, never the current bundle. The broader hostile-storage mutation family and exact release certification remain Level 3.

The package-index and release authority have their own installed-root negatives. Package bytes without the verified product release decision cannot publish a version or select a pointer. The first-party release action publishes the exact decision/version once, survives retry and JSONL reopen, and selects only that version under the expected pointer; stale authority or a competing pointer leaves the parent selected and exposes no child schema. With an otherwise selected child, mutate index bytes without updating the installed package fingerprint, then supply a self-consistent index mapping that selected version to a different otherwise valid bundle: factory capture followed by `get_tool_schemas` must produce no pin/schema, operation, fact, event, network or seed fallback. After a valid pin, change the version-to-bundle mapping and reopen JSONL; submission and protected read are unavailable with zero items/counts/snippets. These checks detect both an omitted index-fingerprint check and an omitted selected-version/bundle equality check.

Build a valid release fixture from source members in the specified nonrecursive order, then independently mutate the decision bytes, compiled release-root pin, package index and one descendant member; each mutation denies unless the product release builder recomputes every permitted downstream digest and authority. In an otherwise valid verified Hermes factory, omit only its call to the core release installer: turn capture still retains source, the seed pointer remains selected, and no child decision/version/selection/pin/schema/fact/event/network effect occurs. Restore that caller and assert one exact decision/version publication, one pointer selection and the child schema. This distinguishes actual installed release reachability from a helper-only package verifier.

Start the verified factory over fresh empty JSONL, an existing exact seed pair, a partial or substituted genesis, and two concurrent first-start processes. In the empty and concurrent cases the core seed-genesis action must produce or accept one complete pair before the release decision/version and pointer CAS; then the installed child schema can be pinned without a model key. Existing exact seed reuses the same bytes. Partial/substituted genesis denies release and schema without repairing it or choosing the packaged child. Repeat the omitted-installer test from an existing exact seed pair so it isolates the missing factory caller rather than the distinct genesis prerequisite. A crash after genesis but before release retries from that same verified parent.

For a captured source, the core structured executor must use `publish_captured_retained_structured_submission` instead of its ordinary two-CAS operation/artifact sequence. It joins the coordination record and source ledger, validates the complete `RetainedStructuredSubmission` and its accepted retained-source operation, and in **one** writer-fenced CAS publishes the new operation link, pending preplanning control, and the canonical envelope/proposal/raw-artifact record that `load_retained_structured_submission` can recover. That same CAS replaces `captured` with `structured_pending` and pins the first operation fence ID. If already `structured_pending`, it leaves the control unchanged but includes its exact record digest as a precondition. `completed_ordinary` and `completed_structured` reject any new operation. A missing, corrupt, or partial coordination record on a source identified by capture ledger or captured-source evidence rejects the operation; ordinary noncaptured sources keep their existing publication behavior. No coordination transition is allowed without the full recoverable immutable proposal payload. Thus abstention, rejection or a crash after the transaction suppress ordinary extraction, and structured recovery has the original bytes; a malformed tool call rejected before the transaction does not suppress. Multiple valid structured operations may share the captured source while it is `structured_pending`; the first operation fence is a durable existence witness, not a limit of one fact. Every publication verifies the current coordination digest in the same store transaction, so a competing completion and operation publication have one winner. After a CAS conflict, reload the control and retry only while its state permits the exact operation. A completion winner denies a late submission even if an old in-memory handle remains. The existing generic noncaptured structured path retains its current contract; the captured-source branch must never fall through to that split path.

The core `publish_captured_turn_completion` owner takes the verified capture ledger, existing admitted user source, prepared assistant admission and a canonical completion preimage containing the exact final user bytes, assistant bytes, session, author, agent, ordinal, and canonical completed-message digest. The `completion_digest` is SHA-256 of `b"memorii.hermes.capture-completion.v1\0"` plus `encode_typed_value` of that closed preimage; callback clock is excluded. It rechecks the user digest and scope against the original ledger and authenticates assistant admission under the same ingress. With `captured` current, it builds the closed canonical ordinary envelope `encode_typed_value({"schema_version": 1, "kind": "ordinary_completed_turn", "capture_id": capture_id, "completion_digest": completion_digest})` and calls `GovernedSourceAdmissionService.allocate_retained_source_operation` with the original captured user `source_id`/`source_digest`, that envelope and the current authenticated ingress. The resulting `RetainedSourceOperationAccepted` supplies the existing core-derived operation ID and `OperationFenceBinding`; the completion owner independently verifies its source, delivery identity, envelope digest and fence. In one writer-fenced conditional transaction it writes the assistant admission closure, completed coordination state, a distinct `semantic_ingestion_captured_turn_ordinary_operation` internal link containing the exact accepted operation/capture/completion/envelope digests, and its normal preplanning control. This link is not a structured-submission marker and cannot pass the structured executor. With `structured_pending` current, the same transaction writes the assistant admission closure and `completed_structured` coordination record with no ordinary link or control; it verifies that `first_structured_operation_fence_id` names an exact retained-source operation link/control **and recoverable immutable submission artifact** for this captured source. Both branches precondition the current coordination digest, the retained capture ledger/source digests, absence of the assistant closure, and the semantic writer binding. The writer policy accepts only these complete typed transaction shapes, preserving the original user source and ledger. It cannot publish assistant evidence separately or enqueue ordinary work before the winning transaction is durably reloaded.

An exact completion retry compares the closed completion preimage digest, assistant admission bytes, chosen state, accepted ordinary operation/envelope when present, and structured operation witness when present to the durable completed record, and returns the existing ordinary pending operation or structured-owned result without another source or control. Changed completion content, identity, scope, or selected owner is denied. If the completion CAS loses to a structured operation CAS, it reloads `structured_pending` and retries the structured branch; if the operation CAS loses to completed ordinary or completed structured, it denies. The provider-local handle enters closing under its lock and waits for in-flight tool calls before asking core to complete; it never restores a handle after restart. The closed completion ABI's canonical full session transcript determines `turn_ordinal` as the one-based count of authenticated user messages through the final supplied user message; tool, assistant, system and developer messages do not advance it. At live completion this ordinal must equal the host `on_turn_start` ordinal retained in the capture ledger; an incomplete or truncated transcript, an ordinal disagreement, or ambiguous final user occurrence denies. Before allowing old two-source completion fallback when no live handle exists, the runtime uses the verified installation, session, principal, agent, this canonical ordinal and digest of the exact final user bytes to search the durable captured-turn ledger and captured-source evidence. Exactly one fully joined capture is completed or retried through its stored ordinal and coordination record without recreating tool authority. Any partial, corrupt, changed or multiple matching captures at that exact coordinate deny; only proven absence permits fallback. A mismatched, ambiguous, expired, closing, or corrupt *existing* live capture also denies rather than falling back. The recovery sweep reads completed coordination records: it enqueues only the exact ordinary pending operation when `completed_ordinary`, and leaves structured operations to their existing recovery owner when `completed_structured`; `captured` and `structured_pending` without completion remain inert. It never rebuilds assistant bytes or a proposal from an incomplete callback after restart.

The host resolves each quote against the retained user segment, not against the assistant message or tool arguments. If text repeats, `source_quote_start` selects one exact Unicode-scalar span under the existing text-span grammar; without an offset, multiple matches are ambiguous and reject. Every subject, predicate anchor, and object quote must lie within the selected assertion span. The host constructs the existing typed `SourceSpanReference` and canonical proposal bytes from the retained artifact and validated offsets. The usual source-normalization, quotation, speaker, trust, semantic, temporal, scope, catalog and lifecycle checks still decide whether the proposal commits. An exact quotation does not by itself establish a fact.

The tool's `proposal` subgrammar has `abstained=false`, exactly one `facts` item, one subject mention and, for an entity object, one object mention; `corrections`, `retractions`, `action_states`, and `identity_operations` are empty. The fact has `commitment=asserted`, `polarity=positive|negative`, and no attributed speaker; other commitment forms require a later distinct tool contract. The fact's `assertion_quote` equals `source_quote` byte-for-byte and its `predicate_anchor_quote` equals the outer `predicate_anchor_quote`. The fact's `subject_entity_ref` resolves only to the subject mention, whose `mention_quote` equals `subject_quote` and whose `mention_context_quote` equals `source_quote`. For an entity object, `object.entity_ref` resolves only to the object mention, whose `mention_quote` equals `object_quote` and whose context equals `source_quote`; no unreferenced mention is allowed. For a literal object, there is no object mention; the outer `object_quote` must resolve exactly in the assertion and the catalog's registered literal parser must derive the proposal's `literal_type`, `canonical_value`, and `unit` from that text. Every temporal qualifier quote must resolve uniquely inside the same assertion. Subject, predicate, object, and temporal spans must each have one unambiguous occurrence inside the selected source span; repeated text without an explicit offset is rejected rather than guessed. The host rejects any mismatch before constructing `StructuredFactSubmissionRequest`; the core semantic validator still has final authority over extraction and truth status.

The verified local factory resolves `AuthenticatedPrincipalAgent` from its pinned installation/operator and canonical agent ID, and issues three separate current versioned authorities for the retained source scope, intended fact scope, and selected catalog-owner visibility. Core selects the packaged catalog and checks any expected digest assertion. The configured host resolver must attest those grants to `ProviderMemoryService.submit_structured_fact`; the adapter never constructs an accepted authority from its tool arguments. Each grant is independently revocable. The semantic writer checks their current state in its final native CAS, and protected status/retry checks current status authority. The completed-turn `prefetch` provisions a `StructuredFactReadAuthority` bound to the same authenticated principal and agent in addition to ordinary scoped-read rows; protected retrieval checks current fact and catalog grants before text, counts, or snippets. A revoked grant denies cached terminal disclosure and read. The separate local structured-tool artifact below authorizes this operation only for the verified installation and packaged profile; it does not imply permission for remote extraction, ontology activation, or other accounts. Expiry or mismatch makes structured writes and reads unavailable or denied under the existing closed statuses, without a network fallback.

The local factory grant issuer derives one stable `grant_id` per `(installation_id, operator_id, canonical_agent_id, grant_kind, scope)`: `hermes-local-structured-grant:v1:<grant_kind>:<hex-digest>`, where the digest is SHA-256 of `b"memorii.hermes.local-structured-grant.v1\0" + encode_typed_value((installation_id, operator_id, canonical_agent_id, grant_kind, scope))`. The initial `grant_version` is 1. The source grant's scope string is `task:` followed by the pinned project task namespace, the fact grant's scope is `user:` followed by the pinned operator ID, and the catalog visibility grant's typed scope is the core-selected `CatalogAuthorityScope(schema_version=1, kind="base")` with `purpose="visibility_status"`; its digest is not a scope or grant identity. The factory issues all three from verified installation material and the current local structured-tool authorization, never from tool arguments. The `StructuredSubmissionAuthorityRequest` carries these exact issued values, and the resolver rejects any altered grant, scope, version, principal or agent before core selects the packaged catalog. Before advertising the tool or capturing a tool-capable turn, a new core provisioning operation writes the three typed active grant states in one same-store CAS under the semantic writer binding and verified factory issuer. An exact active trio is an idempotent retry; partial, substituted or revoked state denies startup and cannot be rewritten as active. The existing retained-submission grant CAS later requires that trio and never initializes a missing state for this local tool. An authorized operator may revoke any one deterministic full typed grant coordinate before or after provisioning. The core revoke operation requires the verified issuer and semantic writer binding; when the state is absent it CAS-inserts an inactive `StructuredGrantState` tombstone at that grant ID, when active it CAS-replaces it with the inactive state, and when already inactive it returns idempotently only for the same grant. It never reports success before the inactive state is durable. Provisioning requires all three absent in its winning CAS or all three exact active on retry; any inactive tombstone, partial state or conflicting CAS result denies. Thus revoke-before-provision and provision-before-revoke both end with that grant inactive, including cross-process CAS races. A revoked state remains revoked across sidecar refresh, process restart and another tool call: the local v1 issuer does not silently increment a version or reactivate it. A future explicit regrant needs a separate authorized contract. Read authority reconstructs only the same fact and catalog grants and checks their current states. Missing current tool authorization, partial grant-state publication or a different installation denies without a substitute credential.

The no-egress structured tool uses a distinct local operator artifact at `<hermes-home>/memorii/local-structured-tool.json`, leaving the closed `local-level2.json` schema and fixed OpenAI extractor acknowledgement unchanged. A new first-party `authorize-local-structured-tool --hermes-home ... --acknowledge-local-memory` action requires an already verified local-Level-2 installation sidecar, but never an OpenAI API key or egress acknowledgement for this new action. It atomically writes canonical JSON plus a terminal newline, with duplicate/unknown fields rejected on load. Its closed fields are `schema_id="memorii.hermes.local_structured_tool_authorization"`, `schema_version=1`, `installation_id`, `hermes_home_digest`, `bootstrap_sidecar_digest`, `profile_selection`, `profile_manifest_digest`, `issued_at`, `expires_at`, `operator_acknowledgement="local_structured_fact_no_egress"`, and `authorization_digest`. The digest is SHA-256 of `b"memorii.hermes.local-structured-tool-authorization.v1\0"` plus canonical JSON of all prior fields. The lifetime is seven days from issuance. The verifier rechecks exact installation/home, current bootstrap sidecar digest, packaged profile identity/digest, acknowledgement, canonical bytes and expiry at factory construction, tool advertisement, every tool call and protected prefetch. The old sidecar alone continues the old extraction path but advertises no structured tool; the new artifact alone cannot bootstrap a Memorii runtime. The new artifact authorizes no model egress, catalog activation or other principal. A changed/expired/revoked artifact closes tool and structured reads without changing old OpenAI extraction authority. Tool authorization may be refreshed only by the explicit first-party action; refresh does not reset a revoked same-store grant. The first installed no-key journey uses both local artifacts with `OPENAI_API_KEY` absent; no transport is constructed or called for capture, structured submission or protected recall.

For this tool, `source_quote` must equal one exact retained `PreparedSource.sentence_spans` substring in the captured user message. The host maps `source_quote_start` to that span's Unicode-scalar start in the original retained message through its verbatim text mapping proof; a supplied offset must match exactly. Without an offset, two matching sentence spans are ambiguous and reject. A normalization, segment boundary or non-verbatim mapping that prevents an exact retained-message join rejects; arbitrary multi-sentence quotes are outside this first tool. The host supplies that stored `SourceSpanReference` as the sole `exact_source_spans` member and never constructs a new span from tool text. It then resolves each subject, predicate anchor, object and temporal quote uniquely inside that sentence; the closed proposal subgrammar above must match those exact strings and the catalog literal parser remains authoritative. The provider callback supplies parsed arguments rather than raw JSON bytes, so `raw_proposal_artifact` is the host's deterministic `encode_typed_value` of the validated closed argument object, with its SHA-256 digest; `proposal_bytes` is the existing canonical encoding of the typed `ProviderSemanticProposal`. The protocol version is `memorii.hermes.structured-fact-tool.v1` and the parser version is `memorii.hermes.retained-sentence-parser.v1`. The host rejects malformed/extra fields as `rejected`, missing or ambiguous retained evidence as `unavailable` or `rejected` according to whether evidence is absent or arguments conflict, and current-authority denial as `denied`. None of these failures creates a retained structured submission or model call.

The production binding has these exact owners. The bridge `on_turn_start` calls a new completed-turn-runtime user-source capture method with host session, ordinal, pinned author/agent, message bytes, and factory-issued ingress; the runtime delegates to the captured-turn admission owner extending source-only atomic publication. Bridge `handle_tool_call` passes only parsed proposal/quotes and its context-local coordinate to a runtime method; the runtime reconstructs references from the retained source, asks the factory-installed resolver for current grants, and calls `ProviderMemoryService.submit_structured_fact`. That service owns identity, catalog selection, validation and the atomic writer. Bridge `sync_turn` calls runtime `complete_captured_turn` when capture exists, or the existing two-source admission when absent. The runtime is the sole callback-join owner. Runtime `prefetch` issues ordinary scoped rows and typed structured read authority to `ProviderMemoryService.retrieve_context`, which owns protected filtering. An absent owner at any hop rejects or reports unavailable before mutation. A helper with no installed caller cannot satisfy this contract.

## Projection-era pre-catalog read correction

For `bootstrap_v3_claim_assertion` records, the legacy verifier accepts only an exact committed group result/reload pair with `group_result_schema_version` 2 or 3 and native projection-publication evidence from the writer that created the projection. It still consumes the caller's one `(revision, records, grant)` snapshot after the ordinary SEMANTIC scope gate, excludes all `retained-source:v1:` and structured-submission markers, and never assigns a new catalog owner or digest to old facts. Its return remains `verified|not_legacy|unavailable`; malformed or incomplete same-scope history makes the whole protected result unavailable with zero items and counts.

The verifier must join the unique original group primary, ordered operation results, fanouts and effect closure to the admitted source, source admission index, claim records and immutable canonical event batch. It must decode the typed core/reload at their stored version and validate the original source, scope, operation, transaction, graph revision and result digests. It requires the exact `IngestionObservationDelta` and immutable observation ledger entry named by the reload; the ledger entry must join the same result locator and group. A committed group requires the typed native projection-publication receipt named in the core/reload, its persisted receipt artifact, replay-authority and checkpoint evidence, original graph-revision delta artifact and canonical event batch. The graph delta and batch must agree on every changed record. Regenerate the complete runtime projection set from the committed `ClaimAssertion` records and original source and compare every published projection byte-for-byte, including the target. For schema 3, additionally validate the original immutable transaction-group commit attestation member and its digest against the committed result and batch. Schema 2 must not be rejected merely for lacking a schema-3 seal. Do not compare mutable current replay-state or reference-ledger snapshots to their historical values after later commits. Unknown version, missing member, wrong cardinality, substitution, extra conflicting member, or any mismatched coordinate is unavailable; never try a weaker schema-1 fallback.

The existing native group recovery validators (`_verify_native_group_entry_snapshot`, `_verify_group_commit_seal_snapshot`) define the versioned artifact joins and should be reused or factored for a caller-supplied snapshot without a second storage read. Their current checkpoint conflict verifier compares the old checkpoint binding to today's mutable conflict tip; that comparison is inappropriate for historical reads. The historical reader validates the checkpoint's typed signature and canonical semantic-conflict binding digest and repository identity as immutable evidence signed by that checkpoint, alongside retained-prefix validation for temporal/trust history. It does not compare the old conflict binding to today's conflict pointers. A missing, invalid or unsigned historical conflict binding is unavailable. Current authorization remains the resolved SEMANTIC fact grant, with the existing release-time recheck. The verifier inspects internal source records only as provenance and releases neither source text nor internal artifacts. A later unrelated group may advance replay and conflict state without invalidating the old committed claim.

Two positive compatibility fixtures must be persisted by authentic projection-era writers through a production composition root: one group reload at schema 2 without a schema-3 seal, and one at schema 3 with its commit attestation. Each must contain a real `bootstrap_v3_claim_assertion` record and read beside a newly catalog-bound claim in the same scope through the protected production root, including JSONL reopen. The schema-3 fixture must fail closed if its attestation is absent or substituted; a schema-2 group must not acquire schema-3 authority from an unrelated attestation artifact. Each fixture then mutates its old closure families separately: primary/reload, admitted source and source-admission-index (missing, substituted or wrong source/group), fanout, result/graph/event/observation effects, ledger entry, receipt, replay evidence, graph delta and canonical event batch. Both versions must still read after a later unrelated conflict transition and resolver-pointer update; missing/invalid checkpoint signature, missing/unsigned/malformed historical conflict binding, foreign repository identity and substituted binding must fail closed. For each version, mutate storage after the caller snapshot and prove the verifier uses only that snapshot; revoke the current SEMANTIC grant after validation but before release and prove zero items, counts, snippets or source text. JSONL reopen and protected reads must leave old record bytes unchanged and create no catalog binding. Current grant denial and inaccessible other-scope corruption are checked. The old writer's schema-1 groups without these runtime projections are outside this reader's positive fixture. The broader Level 3 migration and rollback evidence remains with the implementation WorkPlan.

## Verification and release boundary

The first installed no-key test uses the actual first-party factory, bridge tool schema and callback path, absent `OPENAI_API_KEY`, blocked socket/DNS egress, and JSONL restart. It proves signed-in source capture, one typed tool proposal, native terminal, exact retry, protected later prefetch, and no second ordinary terminal, fact, event or model call after the structured tool submission, including completion racing an in-flight tool call. It checks deterministic grant IDs/versions and exact retry across restart, no grant coordinates accepted from tool arguments, independent source/fact/catalog grant revocation before commit and fact/catalog revocation before read/status, including no silent reissue after sidecar refresh. It checks duplicate callback, wrong account/agent/session, missing turn context, fabricated or ambiguous sentence quote, wrong Unicode-scalar offset, non-verbatim or wrong-segment source, a two-assertion outer/inner quote mismatch, entity and literal object grounding, forbidden extra proposal operations, disabled tool and expired sidecar. A test-only injected resolver does not count as installed proof.

The completion proof runs both source-wide CAS orders: a complete retained operation **and proposal artifact** win before completion and suppress ordinary extraction, or completion wins first and rejects a late operation. It also tests two parallel structured operations on one capture, pending and noncommitting structured terminals, a malformed tool call before retention, exact and changed completion retries, duplicate and overlapping callbacks, and process restart immediately before and after each winning CAS. A crash at the former split operation/artifact boundary must recover an all-or-nothing complete structured payload; no orphaned operation/coordination transition is accepted. Restart after capture but before completion must resolve exactly one durable capture without restoring a tool handle, while a genuinely absent capture retains the old fallback. Two same-text captures in one session with distinct ordinals must complete or retry their own coordinates after restart; a changed, truncated or ordinal-mismatched transcript and duplicate/partial members at one exact coordinate deny. Each case inspects the typed coordination, assistant admission, operation link/control, canonical ordinary envelope or structured artifact, user source, and event/claim sets; missing or substituted coordination/ledger/link members deny rather than creating a second user lineage. The ordinary branch must recover its one exact core-allocated pending operation after restart; the structured branch must not queue it. No test may count a local helper invocation as an installed callback or a post-crash in-memory handle as recovered authority.

The installed matrix separately proves: bootstrap sidecar alone exposes no structured tool, structured artifact alone cannot start the old runtime, both artifacts with no model key expose the tool and make zero network calls, and either artifact's expiry/substitution closes only its authorized path. It provisions the grant trio before tool advertisement, revokes each one before any submission in separate runs, then checks denial of first use, status and read after restart. Two-process or equivalent CAS interleavings cover absent-state revoke before provision, provision before revoke, and both CAS-conflict retries: revoke success always means a durable inactive state, and no outcome advertises an active revoked grant. It also pauses each final native CAS after resolver validation, revokes one grant, then checks `authorization_revoked_before_commit`, no fact/event/catalog binding disclosure and no successful retry. Removing the factory resolver, capture owner, submit caller or read authority from an otherwise valid installed composition must hide the tool or fail protected read with zero items/counts; restoring the exact authority restores the read. A restarted bridge may verify its durable capture ledger but cannot revive the former live tool handle; a call before a new authenticated turn is unavailable. Repeated subject, predicate-anchor, entity/literal-object and temporal text inside one unique sentence must reject without guessing an inner span. Extra top-level IDs, grants, catalog coordinates, unknown schema versions and malformed arguments reject before any write. Every tool result contains only `status` and an eligible `operation_id`, never quote, proposal, source, grant or catalog values.

The legacy test uses the authentic schema-2/3 projection-era fixture and versioned mutation matrix specified above. It includes a mixed accepted/nonaccepted group: accepted operations require their graph and event effects, and nonaccepted operations must not gain those effects. The installed tool/capture fixture also checks crash boundaries, exact recovery, invalid or ambiguous quotes, forbidden proposal operations, revoked grants and no-network execution. Focused Level 2 checks prove the first installed journey and common restart/denial failures. The parent implementation WorkPlan retains the broader Level 3 migration, rollback, CI and release evidence. No milestone closes from this design document alone.
