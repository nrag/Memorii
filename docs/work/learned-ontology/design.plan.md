## Objective

Specify a substantial default ontology for organizational and at-home memory, then a framework-neutral learning path that extends it from retained, scoped evidence supplied by any authenticated agent integration. The base must support useful typed facts and protected recall before learning runs. Learned candidates must be validated and activated under their scope owner without promoting an unvalidated fact. The design must be sufficient for a separate implementation operation.

## Completion Contract

The canonical design identifies twenty organizational coverage personas, at least twenty base entity types, the required typed relations and home scenarios, and measurable acceptance for each base relation before it may count as shippable. It specifies provider-optional monitoring, trajectory attribution, typed discovery, paired evaluation, calibrated or owner-reviewed agent-local activation, and no-key behavior; maps runtime, persisted, and authorization boundaries to core entry points and adapter obligations; records discriminating feasibility evidence; defines verification and identity ledgers; and passes the `$build-design` independent and final review gates with no unresolved validated P1/P2 or approval blocker. Completion is design approval, not implementation or rollout certification.

## Scope

Included: a default catalog serving twenty organizational personas and at-home scenarios; at least twenty shared entity types plus necessary home types; typed relation families with domain, scope, evidence, temporal, correction, and read policies; ontology discovery from any authenticated source adapter; typed additive relation proposals; catalog ownership across authorized scopes; scope-authorized activation; version pinning, source replay, protected reads, and failure behavior. The installed Hermes path is one conformance mapping.

Excluded: fact truth inferred from catalog acceptance; arbitrary schema edits, model-defined executable validators, and harness-specific ontology authority. The design must define cross-scope promotion restrictions and the activation-policy boundary; it need not implement every adapter's identity binding.

Implementation and rollout sequencing, operational hardening depth, release evidence, and migration deployment strategy belong to future implementation and rollout plans. Personal user-context and enterprise catalogs require their own domain policies, but they use the same ontology candidate and version contract when those policies are registered.

## Constraints And Invariants

The candidate/committed, source/projection, domain-routing, and protected-read distinctions in root `AGENTS.md` govern. A model proposes only; deterministic validation and scope-authorized activation own durable change. A new catalog must not reinterpret in-flight operations or historical facts. Source replay uses normal fact-ingestion validation. Unsupported source remains evidence only. Every adapter must carry authenticated provenance and scope; none owns ontology authority.

## Problem Definition And Baseline

The three project predicates in `project_assertions.py` and the installed JSON catalog are a narrow trial seed, not the default ontology the user wants to ship. The adapter's `_PREDICATES` and schema enum are fixed, and `project_assertions_profile.py` requires exactly three catalog entries. `CurrentBootstrapV3Materializer` embeds a content-addressed predicate catalog in each proposal request. The installed Hermes path and live Windows Docker result prove conversation-to-commit-to-recall for a registered predicate in one integration. They do not prove broad default coverage or ontology learning. The product needs a usable base across work and home, then governed candidates for genuinely unsupported concepts encountered by any authenticated agent.

## Decisions, Assumptions, And Open Questions

- Decision: the initial edit language starts with additive relations. Renames, constraint changes, and deletions need separate compatibility contracts.
- Decision: scope-authorized activation is a core operation. A validated agent-local relation may be accepted by the owner; automatic acceptance requires owner enablement, three independent lineages in two sessions, calibrated confidence at least 0.95, a one-sided 95% precision lower bound at least 0.95 for the binding/cohort, and mandatory paired-case passes. These thresholds are proposed, not empirically certified.
- Decision: packaged catalogs, including the three-relation profile, may be immutable seeds and rollback targets without becoming the canonical source of all learned ontologies.
- Decision: the first shipped default bundle must be materially broader than the three-relation trial seed. Twenty cross-functional personas are a coverage heuristic, not twenty entity subclasses or a statistical ranking. Twenty shared entity types plus home forms and their typed relations are the starting catalog, not a ceiling on future learning.
- Decision: the default bundle specifies 53 binary semantic relation IDs, plus a distinct user-context preference record. Family/caregiving relations use separate stable binary IDs rather than a ternary qualifier unsupported by the current fact shape. `TimeInterval` and `Money` require registered typed codecs; until built and tested, those relations cannot count as shipped.
- Decision: the semantic catalog and provider prompt/model/transport binding have independent identities and must pass an explicit compatibility check. A model or prompt change does not change ontology meaning.
- Decision: no OpenAI API key is required by the ontology contract. The model capability may be provided by the host, a local model, or an explicitly configured remote provider. With no such capability, raw-text ontology discovery remains pending while the shipped base, retention, structured fact validation, protected recall, and manual proposal/review remain available. The existing installed fact extractor has separate model dependence that the design must not conceal.
- Decision: adopt EvoOntology's trace diagnosis, attribution to the affected layer, localized typed edit, and paired parent/candidate evaluation. Do not import its data-agent store layout or interpret its benchmark results as Memorii evidence.
- Decision: catalog-owner authority and canonical fact memory scope are separate. Each fact uses its domain's closed scope type and protected reader filters.
- Decision: the evaluation gate is per-case correctness with mandatory withheld positive, negative, regression, and protected-read cases; it makes no statistical certification claim.
- Feasibility result: the installed root cannot carry a fourth relation because package verification, materialization, response schema/adapter, and planning state rules are all fixed to three. The design no longer claims a fourth relation reaches the production writer; implementation must generate and test the entire chain before counting any additional relation as shipped.
- Migration result: current seed-profile claim projections lack a stable per-claim catalog digest, and the sidecar package digest is not per-fact migration authority. The design forbids automatic remapping; old records use a separately verified legacy reader until an explicit evidence-backed migration exists. This avoids inventing historical meaning from the current active catalog.
