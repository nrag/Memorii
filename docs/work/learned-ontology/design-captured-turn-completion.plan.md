## Objective And Evidence

Make the approved captured-turn completion transition derivable without inventing persisted semantics in implementation. A captured source is already stored with one typed `HermesCapturedTurnLedger` and deterministic `PreparedSource`; a retained structured submission has a separate per-operation record. Current `HermesCompletedTurnRuntime.complete_captured_turn` publishes the assistant source in one CAS and then enqueues ordinary user processing in memory. It does not durably mark capture completion or atomically choose structured versus ordinary ownership. A crash or retry can therefore violate the addendum's one-lineage/one-owner requirement. The installed tool worker stopped before implementation. It did close one adjacent bug: active captured-turn mismatch now raises rather than falling back to the two-source completed-turn admission; two focused runtime/bridge checks passed. No installed tool success or milestone completion is claimed.

## Completion Contract

The canonical addendum must specify exact typed persisted completion and source-wide submission-detection identities, immutable versus mutable fields, CAS preconditions and writer policy, assistant/source admission closure, the ordinary-operation fence when selected, and recovery behavior for exact retry, changed completion, crash between callbacks, simultaneous tool calls and completion, and competing sessions. The contract must preserve the captured user source and distinct assistant evidence without a duplicate user observation. It must define which submission states suppress ordinary processing and how the decision is serialized with submissions. A production-entrypoint binding and focused test matrix must be sufficient for an implementation worker to build the transition without selecting new semantics. The frozen correction then receives targeted independent spec, correctness and test review with no remaining validated Level 2 P1/P2 or contract-conformance blocker.

## Scope And Constraints

Included: the callback completion transition, its typed durable record/index, source-wide submission ownership gate, same-store transaction and restart/retry interpretation, and necessary changes to the reviewed addendum's transition paragraph and validation matrix. Excluded: ontology grammar, general catalog and learner, tool proposal syntax, household sharing, protected prefetch, old-schema reader, and Level 3 release evidence. The captured user observation remains inert until one authorized operation owns it. The assistant is evidence only. A model response or callback text cannot mutate committed truth without the existing validators. Existing source/fact/catalog grant revocation still applies to structured writes and reads.

The typed completion record, index and names must be behavioral identities, not this WorkPlan ID, requirement number or milestone. Current `SemanticIngestionAtomicStore` has source-only and retained-submission CAS owners; the design must choose one canonical owner and not introduce an integration-side write. No new public API semantics are authorized by this bounded correction.

## Alternatives And Feasibility Questions

One candidate is a new per-capture immutable completion record plus a per-captured-source submission marker, with both completion and retained submission serialized through one same-store CAS precondition. Another is a mutable capture ledger state; it risks replacing the original capture evidence and requires an exact version/retry policy. A snapshot scan without a shared fence is insufficient because a submission could appear after the completion read. Assess whether the existing operation fence and `RecordAbsentPrecondition`/`RecordDigestPrecondition` can carry the required source-wide choice or whether a new typed per-source coordination record is necessary. The record must not treat a rejected pre-retention tool argument as a retained submission. If an operation is retained before terminal commit, it must suppress ordinary extraction even after abstention or rejection.

## Validation And Review Matrix

Prove no-key installed capture -> retained structured submission -> assistant completion -> one structured owner and no ordinary operation; capture -> completion without a submission -> one ordinary operation; exact retries preserve record identities; changed user/assistant/session/ordinal reject; malformed or denied tool call before retention does not suppress ordinary processing; retained pending/noncommit submission does suppress. Test tool/completion interleavings on both CAS orders, duplicate and parallel calls, crash/reopen before and after completion CAS, and assistant evidence retention with no duplicate user source. A source-wide marker is checked against the exact retained-submission and captured-source identities; missing/partial/corrupt members fail closed. The matrix distinguishes deterministic local checks from CI and live-provider claims. Identity hygiene checks must reject planning coordinates in any new persisted schema/record ID and allow legitimate protocol versions.
